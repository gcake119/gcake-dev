狀態：規劃文件。未實作、未執行產品測試、未建立排程、未部署。既有自動發文及 RSS 通知維持原狀。

## 已確認的產品決策

| 項目 | 決策 |
| --- | --- |
| 納入範圍 | 所有本站系列與獨立文章自動納入，不逐篇或逐系列設定 Hermes。 |
| 檢查頻率 | 沿用單一既有工作，每６０分鐘一次。 |

| 逾期後公開 | 合併為一則新文章暨逾期恢復通知，不再另發同一文章的恢復訊息。 |

單輪內重試不增加輪數。檢查缺席不算正常或異常，也不能接續湊滿連續兩輪。一般來源持續故障且沒有恢復時，依目前已確認的通知範圍，不會推播。

## 資料來源與判定邊界

Git 保存文章與系列閱讀順序；D1 是唯一正式發布佇列。Hermes 保存觀察與通知紀錄，不能反過來改變發布狀態。

正式排程摘要必須區分「承諾」「預估」「未排程」「暫停」「取消」及「無法確認」。ready、週一／週四規則、閱讀順序或 CMS 預估日期，都不能代替正式承諾時間。若 D1 尚未保存承諾，文章仍自動納入，但逾期判定保持待確認。

每輪必須取得當輪有效摘要與公開來源證據，才能判定逾期。讀取失敗不能當成文章不存在；正式文章頁已公開但 RSS 延遲，也不能告警「逾期未發」。Actions 綠燈不等於文章已公開。

## 建議架構

在既有 Worker 增加最小唯讀摘要，Hermes 使用公開 Git、RSS 與正式頁面，搭配摘要取得正式時間。摘要讀取不得觸發 ingestion、排程更新、預約、公開驗證寫入或部署。

設計建議採用「只允許讀取此摘要」的專用憑證，避免 Hermes 持有 Cloudflare 帳號 token 或正式發文密鑰。這是可供審閱的架構建議，並不表示已核准建立憑證或部署；本輪沒有配置任何秘密。

維持單一發送者及單一既有 job。新監控必須銜接既有 sent／unknown／baseline 紀錄，不得重新初始化造成歷史文章重送。交接指出正式 monitor 使用 SQLite，但 repository 歷史文件描述 JSON；實作前須唯讀核對真實格式，不能假設兩者相同。

## TDD 順序

１．核對實作基準、Worker 唯讀整合位置、正式時間語意，以及 Hermes 正式狀態格式。

２．依既有 Given／When／Then 寫驗收測試，保存因未支援產品行為而失敗的真實 RED。既有已支援行為作為綠色回歸測試；測試環境或 fixture 錯誤不能冒充 RED。

３．從驗收失敗拆出整合與單元測試，再實作摘要、通用監控及狀態銜接，達成 GREEN。測試使用可控制時間、本機 HTTP／Telegram transport 與隔離狀態，不發正式訊息。

４．確認新測試確實納入既有測試入口，再執行受影響專案的完整本機驗證。線上 CI 失敗先回本機定位，不推送試錯。

５．提出可審閱的正式導入及回復方案，依後續授權部署摘要、配置專用唯讀憑證及切換既有 wrapper。不得新增第二個通知程序或 Telegram poller。

## 驗證及授權界線

本輪只驗證規劃文件的一致性及格式，不執行產品測試。本機 RED／GREEN、完整本機檢查、正式唯讀觀察、Telegram 系統送出紀錄及使用者收訊確認，必須各自保存證據。

本規劃不授權實作、commit、push、合併、部署、配置新憑證、修改正式 job、重發文章、重跑 workflow、切換正式開關、重設 D1 或通知紀錄。既有正式自動發文及通知維持原狀。

每小時查核加６０分鐘寬限，來源可讀且工作準時執行時，逾期通常在正式時間後約６０至１２０分鐘被觀察到；恢復通常在實際恢復後約６０至１２０分鐘被確認。這些不是即時推播或送達期限保證。
