# 2026 iThome 鐵人賽連載企劃與 30 天內容架構

## 1. 文件用途

本文件是 2026 iThome 鐵人賽連載的共用規劃來源，用於後續討論、撰寫與檢查各篇文章。

後續規劃單篇文章時，應以本文件確認：

- 該篇位於整體 30 天敘事的哪個位置。
- 該篇主要處理產品／需求、工程、Coding／AI 協作中的哪條能力線。
- 該篇如何回應整個系列的核心議題。
- 避免文章退化成單純技術教學、工具介紹或每日開發流水帳。
- 避免公開尚未發表產品及合作單位不必要的業務資訊。
- Day 23–27 保留部分彈性，可依實際開發經驗調整。

---

## 2. 參賽定位

### 競賽組別

**Software Development**

AI Coding 是整個學習與開發過程的重要環境，但系列並非以 Codex、Vibe Coding 或特定 AI 工具本身為研究主題。

主要討論的是：

> 當 AI 已經能大量完成 Coding，一個仍在受訓中的開發新手，如何逐漸學會理解真實工作、決定軟體介入的位置、辨認工程邊界，並利用 AI 將這些判斷轉化成可以實際運作的資訊系統？

---

## 3. 系列核心概念

### 核心一：產品／需求能力——「黏著劑」

目前形成的主要產品思維是：

> **資訊工具不一定需要取代既有系統，而可以成為人、工作流程、資料與成熟工具之間的「黏著劑」。**

關注的問題包括：

- 現場原本怎麼工作？
- 真正造成摩擦或斷點的是什麼？
- 哪些工作值得讓軟體介入？
- 哪些成熟工具應該繼續使用？
- 哪些能力逐漸成為產品核心，應由自己的系統負責？
- 如何減少導入資訊工具造成的工作習慣改變？
- 如何把現場語言翻譯成工程問題？
- 如何再把工程方案翻譯成非工程背景使用者可以理解的改善？

簡化成一句話：

> **產品上，我在學「黏哪裡」。**

---

### 核心二：工程能力——「邊界」

實作過程不斷遇到原本合理的方案，隨需求與複雜度增加而超出適用範圍。

因此工程能力的主要學習問題是：

> **如何辨認現在的解法開始撐不住，以及什麼時候需要重新畫系統邊界？**

代表案例包括：

- n8n automation → 完整 application backend
- 複雜 LINE Flex UI → LINE + Web frontend 分工
- Google Sheets database projection → Web frontend 自己負責資料檢視與報表
- 前端 UI 權限 → 後端 authorization
- 功能測試 → coverage / missing behavior verification
- 單一實作問題 → 跨 repo architecture / contract
- AI implementation → review / security / adversarial verification

簡化成一句話：

> **工程上，我在學「邊界在哪裡」。**

---

### 核心三：Coding／AI 協作能力——實作與學習的加速器

AI 不作為獨立的第四條主線，而是貫穿產品與工程學習過程。

AI 的角色逐漸從：

1. 產生自己完全不會寫的程式碼；
2. 協助理解程式與工程概念；
3. 協助 Debug 與探索方案；
4. Coding Agent 執行實作；
5. 依據規格、測試與 review 流程進行工程協作。

同時存在一個重要限制：

> **AI 可以協助解決我提出的問題，但不保證會替我發現自己根本沒有意識到的問題邊界。**

如果問題一直被定義成：

> 「怎麼把 n8n workflow 改得更複雜？」

AI 可能持續協助改善 workflow。

真正需要重新提出的問題卻可能是：

> 「這現在還是一個 automation problem 嗎？」

因此 AI 同時具有兩種效果：

> **讓新手更快實作，也讓新手更快撞到原本可能很久以後才會遇到的工程邊界。**

但「撞到邊界」不代表「有能力辨認這是一個邊界問題」。

---

## 4. 單篇案例的建議分析框架

涉及架構演進、踩坑或工程決策時，可優先使用以下問題整理，而不是單純描述「原本怎麼做 → 後來怎麼改」。

1. **我當時怎麼定義問題？**
2. **為什麼當時的方案在當時看起來合理？**
3. **AI 在這個問題框架裡幫我做到什麼？**
4. **需求增加後出現了哪些異常訊號？**
5. **我和 AI 在哪裡一起卡住？**
6. **什麼事件、測試、使用經驗或外部意見讓我重新定義問題？**
7. **最後重新畫了哪一條邊界？**
8. **如果現在重新做一次，我會在哪個訊號出現時提早重新評估？**

目的不是證明早期方案「做錯」，而是辨認：

> **一個方案在什麼條件下成立，以及條件改變到什麼程度後應重新評估。**

# 6. 30 天整體架構

## Part I｜Day 1–2：AI 都會寫程式了，我到底在學什麼？

### Day 1｜AI 都會寫程式了，我還要學什麼？

**目的：** 建立作者起點與整個系列問題。

歷史背景控制在約半篇：

- 受訓前曾使用早期 ChatGPT 生成個人創作網站。
- RSS 整合 Podcast 與電子報。
- GitHub Pages 測試部署。
- 當時主要使用完整生成、複製貼上的方式。
- 尚無法判斷需要修改哪個檔案或程式碼位置。
- 過去 MATLAB 經驗使程式邏輯並非完全陌生。
- 後來接受少量前端、CSS / DOM、JS / TS 基礎訓練。
- 開始大量透過 AI Coding 進行真實專案實作。

後半提出系列三條能力線：

> 產品上，我在學「黏哪裡」。

> 工程上，我在學「邊界在哪裡」。

> Coding 與 AI 則讓我有能力快速實作、學習，也更快遇到原本不知道存在的問題。

### Day 2｜AI 讓 Coding 變快之後，困難跑去哪裡了？

**目的：** 建立整個系列閱讀方式。

核心問題：

> Coding Agent 可以讓程式基礎有限的新手快速做出系統，但「做出來」之後，需要哪些原本不知道自己需要知道的能力？

避免寫成 AI 工具介紹。

---

## Part II｜Day 3–10：產品上，我開始學「黏哪裡」

主要案例：

**基於長期諮商服務使用經驗而嘗試開發的 LINE OA 諮商所預約管理工具。**

### Day 3｜從使用者經驗開始：第一次不是先想「做什麼功能」

重點：

- 長期使用服務形成的觀察。
- 工作／服務體驗中的摩擦。
- 從問題而不是功能開始。

### Day 4｜為什麼第一版沒有 Web App，而是選 LINE OA？

重點：

- 使用者已經熟悉 LINE。
- 降低新的操作學習成本。
- 對話作為 interaction channel。
- 不要預設所有資訊工具都需要先建立獨立 Web UI。

### Day 5｜不要重新發明別人已經做好的工具

重點：

早期利用既有成熟服務，例如：

- LINE
- Google Calendar
- Google Sheets
- Google Drive
- Mail

提出「黏著劑」概念。

### Day 6｜「黏著劑」到底要黏什麼？

從「功能」改看：

- 人
- 工作
- 資料
- 工具
- 工作流程
- 流程斷點

核心：

> 新系統不一定取代所有工具，而可能只負責補上原本斷掉的地方。

### Day 7｜使用者說的是工作，不是 User Story

重點：

- 現場描述通常是工作情境。
- 從自然語言辨認流程、角色與例外。
- 不直接把使用者說的一句話交給 AI 生成功能。

### Day 8｜第一次把人的工作翻譯成工程語言

可談：

- role
- state
- event
- data
- workflow
- exception

重點是理解過程，不做完整教科書式教學。

### Day 9｜工程語言還要再翻譯回去

重點：

讓沒有工程背景的使用者理解：

- 系統能幫什麼
- 為什麼這樣設計
- 哪些工作不用改
- 哪些地方會改變
- 工程限制代表什麼

### Day 10｜我的系統應該做到哪裡為止？

第一次正式討論 system boundary。

結尾伏筆：

> 當時畫下的邊界，後來並沒有全部成立。

---

## Part III｜Day 11–18：工程上，我開始學「邊界在哪裡」

主要案例仍為諮商所預約管理工具，但重點從產品思維轉向架構演進與 engineering judgment。

### Day 11｜我以為 n8n 可以把整個流程黏起來

重點：

- 為什麼當初選 n8n 是合理決策。
- Automation 對早期 prototype 的價值。
- 不以「n8n 不好用」作為結論。

### Day 12｜當 Automation 開始需要記住「你現在做到哪一步」

重點：

多步驟 LINE interaction 帶來：

- state
- context
- persistence
- branch
- resume / cancel 等問題

開始從 automation problem 走向 application problem。

### Day 13｜加上多角色權限後，我花了幾週還是改不動

重點：

- 多角色
- 權限
- 複雜 state machine
- workflow 維護成本

核心：

> 問題不是「能不能做到」，而是這一層是否仍適合承擔這些責任。

### Day 14｜AI 為什麼沒有叫我停下來？

AI 協作核心篇之一。

討論：

> 如果我一直問「怎麼讓 n8n 支援這個需求」，AI 很可能繼續幫我改善 n8n。

真正需要重新提出：

> 「這還是一個 automation problem 嗎？」

討論 AI 與問題 framing 的關係。

### Day 15｜把核心流程收回 Backend 之後，我學到了什麼？

可談：

- state
- authorization
- data
- domain logic
- API
- error handling

重點：

把核心產品規則放到更適合負責它的位置。

### Day 16｜Backend 解決了，LINE Flex 卻開始塞不下了

重點：

- 選項字串增加
- interaction complexity
- information density
- 管理型操作
- 對話 UI 的限制

提出新的 UI boundary 問題。

### Day 17｜對話介面不是萬用 UI：為什麼最後還是需要 Web 後台

重點：

- LINE 適合的責任
- Web 適合的責任
- mentor 如何協助重新質疑原本的問題空間

避免寫成「LINE 方案失敗」。

核心是重新分工。

### Day 18｜Sheets 也要退場：哪些能力應該收回自己的產品？

完整 Web 後台建立後：

退場：

- Google Sheets database projection
- 依賴 Sheets 提供主要資料檢視／報表

保留：

- Google Calendar：心理師行事曆同步
- Google Drive：電子收據備份
- Mail：寄送電子收據與每日預約摘要
- LINE OA：適合的通知與互動

核心結論：

> 「黏著劑」不是盡量串越多服務，而是知道哪些成熟能力值得保留、哪些責任已經成為自己的產品核心。

---

## Part IV｜Day 19–26：把這些能力帶進真實委託案

主要案例：

**合作單位委託的內部行政流程進度管理工具。**

### Day 19｜第一次把這些經驗帶進另一個工作現場

重點：

- Sim-sik 累積的需求與系統邊界經驗。
- 如何影響後來的需求訪談與提案。
- 第一次把這套思考帶到另一個領域。

### Day 20｜需求訪談時，我開始在腦中找「斷掉的地方」

觀察：

- 人
- Excel
- 文件
- 既有資訊系統
- 通知
- 人工聯絡
- 資料搬運
- 流程交接

核心問題：

> 新工具到底需要補哪一段？

### Day 21｜「案件進度管理」為什麼不是一個功能？

從模糊需求拆成：

- workflow
- state
- role
- transition
- data
- notification
- visibility

展示需求 → 工程抽象。

### Day 22｜Happy Path 畫完以後，真正的行政流程才開始出現

討論：

- branch
- exception
- parallel flow
- closing flow
- 不同角色
- 現實流程與理想流程的差距

不公開實際敏感業務內容。

### Day 23–26｜浮動工程篇

這四篇不預先鎖死正式篇名。

應依近期真實開發工作選擇最具有學習價值的案例。

候選 backlog：

- API contract
- frontend / backend state
- authorization
- test data
- TDD
- test coverage
- missing behavior tests
- E2E
- cross-repo architecture
- SDD
- Agent context
- responsive UI
- Web-only architecture migration
- CI/CD
- Docker / deployment
- security review
- adversarial review
- debugging / RCA
- observability

**選題標準：**

不是：

> 最近學了什麼技術？

而是：

> **這件事情是否幫助理解「如何讓負責連接不同工作流程的資訊工具可靠地存在」？**

每篇仍應回到「工程邊界」。

## Part V｜Day 27–30：三條能力線重新合流

### Day 27｜AI 說「完成了」之後，我現在會問什麼？

內容可依 Day 23–26 實際文章調整。

可能收束：

- test
- coverage
- E2E
- review
- security
- user verification
- architecture verification

核心：

> 「可以執行」與「工程上可以信任」之間還有哪些距離？

### Day 28｜如果重新做一次，我還會選 LINE、n8n 和 Sheets 嗎？

避免簡化成：

> 不會。

更好的結論可能是：

> 有些仍然會，只是我現在更清楚它們是 prototype、integration、interaction channel 還是 product core，以及什麼訊號代表該重新評估。

重點：

- 不否定早期方案。
- 區分「當時合理」與「後來超出適用範圍」。
- 展示 engineering judgment 的形成。

### Day 29｜如果 AI 寫了大部分程式碼，我為什麼還需要懂 Coding？

核心不是：

> AI 會寫錯，所以我要自己全部重寫。

而是 Coding literacy 讓開發者能夠：

- 閱讀
- 描述
- Debug
- 驗證
- 理解抽象
- 跟 Agent 討論
- 參與工程判斷

這篇回到最早的 Coding 能力線。

### Day 30｜我現在認為 AI 時代的軟體開發是在做什麼？

回應 Day 1。

三條線完整合流：

> **產品上，我在學「黏哪裡」。**

> **工程上，我在學「邊界在哪裡」。**

> **Coding 能力讓我逐漸有能力理解並參與這些判斷。**

> **AI 大幅加速實作與學習，也讓我更快撞到原本可能很久以後才會遇到的工程問題；但當我不知道某個邊界存在時，AI 也可能跟我一起困在原本的問題框架裡。**

最後可再提出第二層「黏著劑」：

> 最開始以為資訊工具是在不同工作、資料與成熟系統之間當黏著劑。

> 後來才發現，開發者本身也在連接現場使用者、產品需求、工程語言、AI Coding Agent 與最終軟體系統。

# 7. 三條能力線的篇幅比重

整體約略比重：

- **產品／需求能力：約 35%**
- **工程能力：約 45%**
- **Coding／AI 協作：約 20%**

實際上單篇可同時跨兩條以上能力線，不要求平均分配。

大致的敘事重心：

```text
Day 01–02   三條線建立
Day 03–10   產品／需求為主
Day 11–18   工程邊界為主，產品與 AI 協作交錯
Day 19–22   需求 → 工程能力轉移
Day 23–26   浮動工程實戰
Day 27–30   三條線重新合流
```

---

# 8. 後半工程篇的調整原則

Day 23–27 應根據比賽期間實際開發工作持續調整。

優先選擇：

- 真正發生過的問題
- 有清楚 decision point 的問題
- 能說明某個 engineering boundary 的問題
- AI 曾參與實作、Debug 或分析的問題
- 可以匿名化公開的問題
- 最後能形成可轉移經驗的問題

避免：

- 為湊 30 篇硬塞的技術介紹
- 單純工具操作教學
- 沒有實際使用情境的名詞解釋
- 與「黏著劑／工程邊界」無關的零散學習筆記

# 10. 寫作立場

系列不應採用「資深工程師教新手」的立場。

作者位置：

> **一個仍在接受開發訓練、但已經利用 AI Coding Agent 實際參與產品與委託專案的人，整理自己如何從無法修改 AI 生成程式碼，逐漸開始理解需求、系統邊界與軟體工程。**

文章可以明確區分：

- 當時不知道什麼
- 當時為什麼這樣做
- 後來發生什麼
- 現在怎麼理解
- 哪些仍然沒有答案

避免把事後學到的知識改寫成「當時早就知道」。

---

# 11. AI 協作的寫作原則

避免將 AI 描述成：

- 萬能工程師
- 永遠會主動發現架構問題
- 只會產生錯誤程式碼的工具

更準確的觀察：

> AI 的能力會受到使用者如何定義問題、提供上下文、設定驗證流程與提出反例影響。

可持續觀察：

- AI 什麼時候幫助快速建立理解？
- AI 什麼時候讓試錯成本降低？
- AI 什麼時候在錯誤問題框架中繼續最佳化？
- mentor / user / test / review 如何補足 AI 協作？
- 自己的工程語言增加後，與 AI 的協作品質如何改變？

# 12. 2026 iThome 鐵人賽規則對內容規劃的影響

依 2026 官方活動簡章：

- 主題競賽包含 Software Development、Vibe Coding、ChatGPT & Codex、AI Engineering 等組別。
- 每日需發表一篇切題技術文章，連續 30 日。
- 每篇需超過 300 字。
- 內容以繁體中文為主。
- 允許使用生成式 AI，但文章仍須符合自創內容規範。
- 引用內容不得超過全文 1/3。
- 評審會看：
  - 主題
  - 結構
  - 內容
  - 表達
- 「結構」特別要求 30 篇文章組織良好，足以引導讀者理解參賽者設定的議題。

因此本系列採：

> **固定整體論述，保留部分工程篇浮動。**

而不是：

> 每天依當天學到的東西臨時決定文章方向。

# 13. 目前暫定系列核心句

可作為後續命名與簡介的基礎：

> **AI 都會寫程式了，我還要學什麼？**

延伸論點：

> **產品上，我在學「黏哪裡」；工程上，我在學「邊界在哪裡」。**

以及：

> **AI 讓我更快實作、更快學習，也更快撞到工程邊界；但當我連某個邊界存在都不知道時，AI 也可能跟我一起困在原本的問題框架裡。**

系列名稱尚未正式定案。

目前可使用工作名稱：

> **《AI 都會寫程式了，我還要學什麼？——一個開發新手的 30 天實作筆記》**

後續可依 Day 1、系列簡介與前 10 篇實際內容，再決定是否把「黏著劑」直接放入正式名稱。
