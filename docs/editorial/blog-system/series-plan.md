# 《我的技術部落格，是怎麼慢慢變成一套系統的？》系列寫作企劃

> 狀態：2026-10-26 更新至第 03 篇定稿；保留 2026-10-25 五章 15 篇企劃基線  
> 用途：本系列的 Git 版企劃基線，供 Project 與後續寫作對話查閱；它不是文章正文，也不是最新程式實作狀態的權威來源。  
> 主要專案：[`gcake119/gcake-dev`](https://github.com/gcake119/gcake-dev)  
> 前置專案：[`gcake119/ithome-2026`](https://github.com/gcake119/ithome-2026)

## 1. 系列定位：先回答什麼問題

**核心問題：當個人的系列寫作方法逐漸成為一套軟體系統，應如何決定內容、操作、資料和發布流程各由誰負責，如何讓它們共同運作，又如何判斷系統真的可靠？**

這是一套**從自己的寫作需求一路推導到 System Design** 的真實開發與學習紀錄。作者在準備 2026 年 iThome 鐵人賽 30 篇連載時，發現「先規劃整套架構、逐篇討論與寫作、完成後再整理收斂、最後依固定頻率排程發布」適合自己整理思考和沉澱觀點，因此決定長期採用。這套工作方式逐步延伸到技術部落格、系列管理、簡易編輯後台、自動發布、外部平台同步、監控及文章搜尋。

**不是** Astro／Cloudflare／Substack 工具教學、術語百科、功能型錄、commit 流水帳，也不寫成「AI 全包、作者完全不需要理解工程」的故事。

寫法採**第一性原理**：先釐清人的工作與基本需求，再推導系統要保證的條件、責任與架構，最後才說明技術選擇和實作。採**金字塔原理**：每篇先給核心論點，再用真實問題、決策原因、實作與驗證證據支持。以繁體中文、白話、完整但不破碎的段落敘述。

## 2. 五個逐步出現的基本問題

1. **如何持續寫作並沉澱思考？** 系列企劃、跨對話狀態、逐篇討論、多輪審稿、全系列整合與定期發布。
2. **如何長期保存與呈現文章？** Markdown/Git、Series manifest、Astro/GitHub Pages、舊文來源、閱讀導覽、SEO/AEO、互動內容。
3. **如何讓日常編輯方便且安全？** ChatGPT/Codex 與圖形介面的工作分工、Vue Admin、Workers、Git/R2/D1、預覽、版本衝突與復原。
4. **如何可靠地把文章發布出去？** 系列資格、固定時段、D1 持久發文狀態、Pages、Substack Computer Use、公開驗證、Hermes 通知、失敗與重試。
5. **文章增加後，如何讓讀者找到內容、讓作者維護系統？** 關鍵字／語意搜尋、公開文章索引、免費額度與降級、ChatGPT→GitHub 文件→Codex 的開發分工、測試與 QA 能力邊界。

上述是**需求邏輯順序**；各功能在 Git 中的實作日期可能交錯，不可把章節順序誤當成每一個決策都依序發生。

## 3. 已確認的個人動機與決策事實（不可改寫）

- **系列文＋先備文、定期排程**：源於鐵人 30 篇備稿期間逐漸確認的思考與整理偏好。先規劃具體架構，逐篇思考，寫完再全系列收斂；固定連載使思考與公開發布可分開。不可說成是先為了自動發文才選系列文。
- **第 01 篇作者確認（2026-10-26）**：規劃架構時就開始看清經驗關係，是主要的思考幫助；先備稿的主要目的為維持固定發表頻率、避免缺稿與趕稿。閱讀更聚焦是期待，尚無足夠回饋可確認成效。系列為核心仍可與獨立筆記、心得並存；鐵人賽備稿 → 延伸閱讀試行 → 決定另架部落格，不把試行寫成比賽結束後才發生。
- **ChatGPT 協作寫作**：30 篇在同一 Project 中，每篇獨立開對話；以企劃、寫作規範、最新銜接紀錄和必要前文提供脈絡。先討論核心與素材，再形成大綱、初稿、多輪審稿和定稿。每篇定稿更新跨篇銜接；最後再整合 30 篇，依完稿重整章節。保留「當時知道／後來才理解／目前仍不知道」。這個過程已有公開文章〈我是怎麼跟 ChatGPT 協作寫完 30 篇系列文的〉，新系列應有新的工程視角，避免大量重寫。
- **簡易 CMS／編輯後台**：動機是減少簡單編輯任務每次都要開 ChatGPT 對話、用自然語言來回交辦的操作成本。複雜內容與架構討論仍適合 ChatGPT/Codex；簡單 metadata、日期、圖片、系列排序和狀態確認適合 GUI。不可假定後台的原始目的就是取代 AI 寫作流程。
- **媒體庫選 R2**：當時不確定應放在 GitHub、圖床或雲端儲存；規劃後台時 ChatGPT 建議 Cloudflare 服務，於是採 R2。至今尚無足夠實際使用資料可評判相較 GitHub 等方案的網站效能、編輯便利性及長期成本。不能補寫成做過完整比較、已證明 R2 最佳。
- **Paragraph 移除**：原本關注透過 Paragraph 發布至 Arweave 的可能性；後來發現相關官方文件連結失效，無法確認是否仍提供該服務，因而移除同步。不可未經另行查證就宣稱官方已確定停止 Arweave 保存。
- **Substack**：缺乏符合需求的正式發文 API，沿用鐵人 30 篇發文時使用的 Codex Computer Use 操作方式，處理草稿、排程及來源／canonical 相關設定。實際外部平台 canonical 支援有限，區分「平台 HTML canonical」和「文章內可見來源連結」，勿一概寫成已設定跨站 canonical。
- **ChatGPT 與 Codex 分工**：作者在 ChatGPT 討論架構、產生 GitHub 初始骨架及文件，再交由 Codex 負責大量 coding；節省 Codex 週額度是考量之一。除非有同條件用量證據，不推導確切節省比例。
- **能力界線**：作者可以參與系統責任、架構、資料流、需求、規格、測試與驗收判斷；不以逐行閱讀或獨立 code-level debugging 為主要工作方式。Happy Path 操作能驗證，但例外、邊界與深層實作路徑仍是學習中的能力。不要替作者製造已掌握完整 QA 或 code-level 能力的成長故事。

### 主要架構的責任模型

- Git：新文章 Markdown／MDX、frontmatter、系列 manifest、編輯歷史及正式內容來源。
- `ithome-2026`：原鐵人 30 篇正文來源；`gcake-dev` 可同步閱讀版本，保留舊 canonical 和完成快照的完整性。
- Astro／GitHub Pages：正式靜態文章閱讀版本與新文章 canonical；建置時產生路由、主題、RSS、SEO/AEO、關鍵字索引等衍生輸出。
- Vue Admin／Cloudflare Workers：簡易編輯操作、身份與 API 邊界、Git 寫入協調、媒體、預覽、排程及發布狀態介面。
- Cloudflare R2：媒體實體檔案；D1：CMS／發布佇列／嘗試／狀態等操作資料，不能成為第二份可編輯文章正文。
- Substack：外部分發目標；沒有適用的正式發文 API，透過受控 Computer Use 流程處理，和 Git/Pages 成功狀態分開驗證。
- Hermes：發布狀態觀察與必要通知；觀察／通知紀錄不能反過來改變發文權威狀態。
- Cloudflare 搜尋 Worker／Workers AI／Vectorize：公開文章的語意檢索及衍生索引，不持有編輯或發布權限；額度不足或服務故障時保持關鍵字搜尋。**不是已提供生成式問答或 RAG 回答。**

## 5. 正式候選結構：五章、15 篇

章節順序依需求形成的可讀敘事安排；標題和篇數可在逐篇討論後微調。每篇應集中一個主要工程問題。

### 第一章｜從寫作方法開始（01–03）

**01｜以「系列連載」為核心的發表形式**  
核心：架構規劃本身幫助整理經驗與釐清想法；期待系列主題讓閱讀聚焦，保留單篇並存；先備稿再固定頻率發表，避免缺稿與趕稿。延伸閱讀試行後，確認能持續整理專案開發想法，才決定另架部落格，未繼續擴充鐵人30。第 01 篇已由作者確認定稿，正文與 manifest 均維持 draft，未公開。  
工程問題：如何把自己的工作方式整理成可重複的流程？  
避免：把自動化說成先於寫作偏好的動機。

**02｜把寫作流程變成 Agent 能接手的固定工作**  
核心：從鐵人賽期間手動更新 Project 來源檔案、補充跨對話脈絡，延伸到企劃與交接模板化、協作規則文件化，連同文章用 Git 管理。減少續寫及開新系列的固定準備與交接工作；先討論主題、真實經驗與論點，由作者確認定稿。第 02 篇已確認定稿，正文與 manifest 維持 draft。  
工程問題：如何將反覆工作整理為 Agent 可遵循、可重用、可持續修改的流程？  
避免：重述舊協作文章完整流程、具體日期與 commit 流水帳；不將最近的 Repo 規則倒寫為鐵人賽備文期已存在。Project 指令參考文件不會自動同步設定，長期維護效果仍待確認。

**03｜讓系列安排跟著實際寫作調整**  
核心：貼合寫作需求，依實際內容調整篇目與閱讀的行文邏輯；系列清單集中保存順序與進度，企劃／交接保留原因。章節是可依需要採用的閱讀設計。第 03 篇已確認定稿，正文與 manifest 維持 draft。  
工程問題：系列安排集中管理、正文與篇序分工，以及定稿與公開的區分。

### 第二章｜從文章網站到長期內容站（04–06）

**04｜有了鐵人賽網站，為什麼還要建立一個新的部落格？**  
核心：從固定 30 篇網站到長期多系列內容站；Astro、GitHub Pages、Markdown、Vue islands 的當時選型條件。  
工程問題：需求範圍和技術架構如何對應？  
避免：未查對話就替當時補出完整框架比較。

**05｜同一篇文章出現在兩個網站，誰負責保存正式版本？**  
核心：`ithome-2026` 與 `gcake-dev` 的權責、外部文章讀取、canonical、完成快照與完整性檢查。  
工程問題：資料所有權、固定快照、跨系統版本一致性。

**06｜文章放上網站後，還有哪些事情要自動處理？**  
核心：靜態建置時一起處理路由、系列導航、主題分類、RSS、SEO/AEO、分享與文章閱讀；必要時帶到 MDX/Vue 互動內容及外部平台靜態替代。  
工程問題：內容轉換、共用規則、衍生資料一致性。  
避免：技術名詞清單，尚未使用的互動教材不可寫成已上線案例。

### 第三章｜為了讓編輯更方便，我做了一個後台（07–09）

**07｜ChatGPT 已經可以幫我改文章，為什麼還需要編輯後台？**  
核心：自然語言很適合深入討論，不適合每次簡單編修都交辦；將適當的工作交給 GUI，保留 AI 深度協作。  
工程問題：使用者工作流程、人機介面選擇、產品邊界。

**08｜文章、圖片和發布紀錄，為什麼要分開保存？**  
核心：當時對 GitHub／圖床／雲端儲存的猶豫，ChatGPT 推薦 R2，以及 Git／R2／D1 的資料分工；誠實保留效能、成本、使用體驗未驗證的問題。  
工程問題：資料生命週期、系統責任、儲存取捨與可逆性。

**09｜編輯後台也能直接改 Git，怎麼避免把文章改壞？**  
核心：Codex 與 CMS 都可能編輯，衝突、SHA、原子提交、草稿回復、媒體引用、正式 Astro 預覽，以及真實 UI 驗收後的修正。  
工程問題：並行控制、完整性、安全操作和驗證層次。

### 第四章｜當連載發布真正交給系統（10–12）

**10｜我只想固定時間發文，為什麼後來需要發布佇列？**  
核心：從 frontmatter 日期與靜態建置到週一／四排程、系列資格、D1 發布狀態、發布身份、Pages 公開證據。  
工程問題：排程、持久化佇列、狀態機、部署延遲。

**11｜沒有發文 API，怎麼把文章同步到 Substack？**  
核心：Paragraph 原先 Arweave 動機和官方文件失連導致的重新評估，Substack 的正式 API 限制；沿用 Codex Computer Use 操作 Chrome 草稿、排程、連結與驗證。  
工程問題：外部依賴、介面契約、不穩定操作環境與隔離。  
避免：把文章內來源連結說成 Substack 跨站 HTML canonical 已成功設定。

**12｜發文成功不能只看系統說了什麼**  
核心：Git commit、Actions、Pages／RSS、Substack、Hermes 等不同證據；實際逾時、重試、誤報、未知結果、重複通知保護。  
工程問題：端到端驗證、可觀察性、冪等性、失敗恢復。

### 第五章｜網站開始長出新的能力，我還需要理解什麼？（13–15）

**13｜文章多了之後，我開始思考怎麼讓讀者找到內容**  
核心：從搜尋頁簡化、關鍵字搜尋和本機語意比較，到 Cloudflare BGE-M3、Vectorize、索引同步、來源版本與免費額度界線。  
工程問題：公開資料與衍生索引的一致性、向量索引生命週期、資源限制和失敗降級。  
避免：把語意檢索說成 RAG 問答，也不可聲稱最新索引修正已完全正式驗收。

**14｜ChatGPT 負責討論架構、Codex 負責實作，這套分工怎麼形成？**  
核心：從 ChatGPT 討論架構、建立 GitHub 初始骨架與交接文件，到 Codex、OpenSpec／Spectra、TDD、review 和人工驗收；包含 Codex 週額度限制、重複 CI 與資源成本。  
工程問題：Context Engineering、規格與任務契約、證據鏈、開發成本。  
避免：沒有量測資料就宣稱節省特定百分比。

**15｜部落格變成一套系統之後，我現在理解了多少？**  
核心：將整套內容系統的資料流與責任串起來，說清楚目前能主動參與哪些決策、哪些結果能驗、哪些 code-level 與非 Happy Path 問題仍需學習。  
工程問題：System Design 與程式碼理解的關係、可靠性、能力界線。  
結尾不要宣稱已解答所有問題。

## 6. 跨篇界線與重複控制

- 01／02：01 是為何選此寫作方式與長期使用的動機；02 是跨對話 context 的交接機制。讀者已可另讀既有〈我是怎麼跟 ChatGPT 協作寫完 30 篇系列文的〉。
- 02／03：02 管理人與 AI 的對話脈絡；03 管理文章與系列的資料模型。
- 03／05／08：03 談系列編輯權威；05 談舊文跨 repo ownership；08 才談 Git／R2／D1 分工。
- 06／13：06 談 Astro 建置時的內容呈現與基本搜尋資料；13 專講語意檢索服務及索引同步。

## 8. 後續每篇對話的工作方式

每篇定稿後，請同時更新 `docs/editorial/blog-system/progress-and-handoff.md`，依 `docs/editorial/_templates/progress-and-handoff.md` 的原則保存精簡交接；新對話優先讀最新交接與必要前文。

每篇文章新開一個對話；讀本企劃、共同寫作規則、必要前文與相關 repo 文件即可，不預設一次讀完整 repo 或 15 篇所有正文。

1. **先定位**：本篇在整套敘事中回答的獨立問題，以及與前後篇的界線。
2. **核對素材**：按需求閱讀最新 repo、關鍵 commit、設計／OpenSpec、驗收證據及既有文章。整理「確定發生、推論、仍不確定」三類。
3. **先討論，後寫稿**：請作者補充當時的動機、實際使用情境、選擇過程和自己理解到哪裡；先收斂核心論點、調整標題，再做簡要大綱。
4. **初稿與多輪審稿**：按核心→事實→跨篇→文字順序。提早破題，小白友善，完整段落，少用不必要的英文工程名詞。
5. **定稿與交接**：輸出完整 Markdown，更新該篇進度、前後篇界線及新的決策事實；如實際內容改變系列規劃，調整尚未寫作篇目，保留歷史。

每篇正式定稿前至少回答：

- 當時要解決什麼具體問題？
- 有哪些真的考慮過的選項，以及選擇依據？
- 哪些想法是作者提出，哪些來自 ChatGPT／Codex？
- 實際做到什麼？有何測試、正式部署或人工驗收證據？
- 當時知道、後來才理解、現在仍不確定的各是什麼？
- 本篇是否重複舊文或提前回答下一篇？

## 11. 跨系列文件架構與逐篇交接（2026-10-26 確立）

此系列本身也實踐文中討論的「規劃 → 逐篇協作 → 定稿 → 持續交接」流程。Repo 同時保留通用模板與各系列獨立文件：

```text

│   ├── series-plan.md                 # 未來系列沿用、跨系列迭代
```

- **通用模板**保存跨系列可沿用的欄位與協作方法；寫作方法改善時可迭代模板，但不自動覆寫已開始的系列。
- **各系列企劃**記錄該系列的定位、時間線、章節與候選篇目，依實際定稿調整尚未公開的安排；不作為其他系列的共用單一企劃。

- **正式 Markdown 與 Series manifest**繼續各自管理正文、網站導覽與編輯發布狀態；交接文件不取代正式內容資料。
- **對話讀取順序**：本系列企劃 → 最新本系列交接 → 上篇定稿及必要前文 → 本篇涉及的 Git／OpenSpec／驗收紀錄。避免每篇重新讀完整 repo。
