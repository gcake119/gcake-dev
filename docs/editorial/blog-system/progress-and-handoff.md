## 全系列固定事實與邊界

- 寫作形式的動機：準備鐵人賽 30 篇文章時，發現「先規劃系列架構、逐篇思考、全系列完稿後重新收斂、固定頻率發表」適合整理思考；不是先為自動發布而選系列。
- 舊寫作模式：ChatGPT Project 保存共用資料、每篇各開對話、討論核心後寫稿、多輪審稿，定稿後更新銜接紀錄。既有延伸篇〈我是怎麼跟 ChatGPT 協作寫完 30 篇系列文的〉已談過具體流程，新系列避免大量重複。
- CMS 動機：減少簡單編輯任務每次都須透過 ChatGPT 自然語言交辦的操作成本，不是為了替代深入的 AI 協作寫作。
- R2 的選擇：當時 GitHub、圖床與雲端儲存的取捨未完全確定；依 ChatGPT 建議採 Cloudflare，效能、編輯體驗與成本尚未充分量測。
- Paragraph：當時無法確認官方仍支援 Arweave 保存，因此移除同步；不能寫成官方已證實停用。
- Substack：缺少適用的正式發文 API；透過 Codex Computer Use 操作 Chrome。區分草稿、排程、真實公開、通知與 HTML canonical／文章內來源連結。
- 技術與 AI 能力：作者能參與需求、系統責任、資料流、規格和驗證討論；仍不足以獨立沿著大型 codebase 追完整 implementation path，非 Happy Path QA 仍在學。
- 寫作時依當篇再次核對最新 gcake-dev Git、OpenSpec 與驗收；企劃歷史的最新 SHA 不能當作永久最新。
