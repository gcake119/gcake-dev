一開始，我只是想解決一件事：30 篇文章會先寫完，開賽後我不想每天再手動登入 iThome 發一篇。

所以最早的需求很直接：30 篇先寫成 Markdown，開賽前匯進 iThome 當草稿，開賽後每天自動發一篇。工具最好也能讓別人 fork 或下載後，換成自己的內容和設定使用。

真的開始做之後，我才發現這些需求沒有辦法全部塞進同一條流程。

賽前一次處理 30 篇、每天正式發一篇、讓讀者看文章、出問題時通知我，雖然都圍繞著同一批內容，實際上是在解不同問題。

## 最早，我想讓 Playwright 從頭做到尾

一開始，我先找到一個用 Python 寫的 iThome 發文工具。

但 iThome 已經改版，舊工具不能直接用。跟 ChatGPT 討論後，改用 Playwright，直接操作當時真正的 iThome 網頁。

最初想得很簡單：

```text
30 篇 Markdown
→ 建立 30 篇 iThome 草稿
→ 開賽
→ 每天找到當天草稿
→ 正式發表
```

也就是一套瀏覽器自動化一路做到底。

實作後才發現，它要真的走過 iThome 的發文入口、選對系列、找到文章編輯器，還要處理頁面載入、草稿網址和真實網站的各種狀況。

等到 Playwright 已經真的能操作草稿流程後，第一個問題出現了。

## 30 篇一起匯入，和每天發一篇，不太一樣

測試把 30 篇文章逐篇建立成草稿時，反覆操作 iThome 觸發了 Too Many Requests。

Playwright 不是不能填草稿，問題是短時間內要對同一個網站做很多次操作。

到這裡，我第一次很明顯感覺到：

> 賽前一次處理 30 篇，和開賽後每天處理 1 篇，雖然都叫自動發文，條件不一樣。

所以我不再讓 Playwright 負責大量草稿匯入。

## Computer Use 適合匯草稿，但每天正式發文又卡住了

下一個想法，是讓 Computer Use 接手。

它可以直接看著網站操作，也很適合這種有人在場、一次處理很多筆的工作。

當時一度想變成：

```text
Computer Use
→ 賽前匯入 30 篇草稿
→ 開賽後每天正式發表一篇
```

最後，賽前大量草稿匯入交給 Computer Use。

但每天正式發文有另一個限制：Computer Use 在第三方網站做正式公開發文時，最後的動作需要使用者當下確認。

如果每天九點半還是要我回來回答一次「同意發文」，就沒有達到我原本要的無人值守。

## 最後變成三個角色

所以原本的一條流程，最後拆成這樣：

```text
賽前大量草稿匯入
→ Computer Use

賽中每日正式發布
→ Playwright / local publisher

發布結果與公開狀態
→ Hermes
→ Telegram 通知
```

Computer Use 負責賽前一次性的草稿準備。

Playwright 最後留下來的工作小很多：每天找到已經存在的草稿，完成最後的正式發布。

這個每天實際執行發文的本機工具，後來就成了 publisher。

到這裡，原本「自動發文」這件事已經被拆成幾個不同責任。

## 後來，我又加了一個自己的文章網站

文章網站不是最早的需求。

我是在做這套工具時，看到別人的鐵人賽系列也有自己的網站，才想讓同一批 Markdown 有一個自己的閱讀入口。

網站一開始只要能顯示文章，後來才補上完整的 30 天閱讀體驗，包括系列目錄、閱讀進度、上下篇、手機版、明暗色主題和「鐵人賽 30」主視覺。

做到這裡，網站負責的問題也很清楚：

> 這 30 篇文章要怎麼讓人一路讀下去？

所以同一份 Markdown，開始走兩條路：

```text
Markdown
├─ 文章網站
└─ iThome 發布流程
```

網站處理閱讀，publisher 處理發布。

## Hermes 解決的是：我什麼時候需要回來

自動通知從一開始就在需求裡。因為如果每天還要打開 Codex 看排程有沒有正常跑，那就還是要每天管。

當時我剛開始學 Hermes，跟 ChatGPT 討論後，就讓它負責看發布結果，再透過 Telegram 通知我：正常就安靜，需要處理時再叫我。

所以 Hermes 解決的是：

> 我什麼時候需要回來？

## 模板解決的是：換一批文章還能不能用

另一個一開始就有的目標，是這套東西不要只能用在我這次鐵人賽。

希望其他人可以：

```text
fork / download
→ 換自己的 30 篇文章
→ 換自己的設定
→ 開始使用
```

也可以直接交給 AI Agent 協助設定。

所以模板要解決的是：

> 換成別人的文章和設定後，這套東西還能不能繼續用？

如果只想要文章網站，也可以不用 publisher 和 Hermes。

更完整的初始化流程、Agent 邊界和完成條件，是正式使用之後才繼續補的。

## 到開賽前，它已經不只是一支自動發文程式

到了 9 月 8 日，30 篇正式文章已經全部進 repo。

正式發文需要用到的標題、正文、日期和網址資料，也都逐篇驗證過。正式日期對齊，網站和手機入口處理完成，每日 publisher 和本機排程範本也準備好。

Day 1 原本就保留手動發布，用來取得正式系列資訊。

真正開始驗證無人值守發文，是 Day 2。

到這時，整套工具已經變成：

```text
Markdown
→ 保存文章內容

網站
→ 負責閱讀體驗

Computer Use
→ 負責賽前大量草稿匯入

Playwright / local publisher
→ 負責賽中每日正式發布

Hermes
→ 負責監控和異常通知

模板
→ 讓別人換內容後也能使用
```

這個分工不是第一天就畫好的。它是在碰到 Too Many Requests、Computer Use 的操作限制，再加上閱讀、通知和重用需求後，一步一步拆出來的。

我原本只是不想每天自己登入 iThome 發一篇文章。到了正式開賽前，它已經變成一套由不同部分各自負責的工具。

接下來才要知道，真正每天跑起來後，它有沒有照預期工作。
