30 篇鐵人賽文章寫完後，我想把這些 Markdown 做成自己的系列閱讀網站。

程式主要還是會交給 AI 寫，但有一件事我還是得參與決定：這個網站到底要用什麼框架？

前端框架可以先簡單理解成：一套幫忙組織網站畫面和互動功能的開發工具。不同框架都可以拿來做網站，只是各自比較常處理的使用情境和預設做法不太一樣。

問題是，我對框架的實作細節、底層機制，還有很多設計原理都沒什麼概念。

所以我當時遇到的問題就是：**如果程式主要都不是我自己寫，那我要靠什麼判斷 AI 推薦的技術合不合理？**

## Astro 是第一推薦，但我沒有直接用

我把需求告訴 ChatGPT：手上已經有一批 Markdown 文章，想做成一個可以閱讀 30 天系列內容的網站。

當時 ChatGPT 提了幾個都可以拿 Markdown 做內容網站的方案，Astro 是第一推薦。

我現在已經不記得全部候選框架有哪些，但當時沒有看到第一推薦就直接開始做。

我有請 ChatGPT 把幾個方案一個一個解釋，像是適合什麼情境、優點在哪、缺點在哪，還有各自有哪些設計取捨。

比較過一輪之後，我才決定用 Astro。

這個決定不是因為我去看過 Astro 底層怎麼實作，我沒有這個能力。

我當時比較能理解的是：**這幾個方案分別適合拿來做什麼，哪一個跟我的需求比較接近。**

## 我還問過：既然其他專案都用 Vue，為什麼這次不用？

我前端受訓的時候，只先學過一些 HTML、CSS、JavaScript 基礎。

當時 mentor 主要用 Vue，也有跟我說 Vue 相對容易上手。後來我開始跟 AI 協作做專案，幾個 Web App 的前端也都直接叫 AI 用 Vue / Vite 寫。

所以 Vue 算是我最常碰到的前端框架，但我對它的框架設計和實作細節也沒有深入理解。

當 ChatGPT 推薦 Astro 時，我很自然就問了一句：

**既然 Vue 也能做網站，為什麼這次不乾脆全部用 Vue？**

Vue 一樣可以做這個網站。

Markdown 文章、文章頁、RSS、SEO、Sitemap、GitHub Pages，這些功能都不是 Astro 專屬。

我後來比較能理解的差別是：**兩個都能做網站，但 Astro 對我這次這種內容型網站更專門。**

## 先不要看框架名字，先看這個網站到底要做什麼

如果先把 Astro 和 Vue 的名字拿掉，我當時的鐵人賽網站需求大概就是：

- 主要內容已經是 Markdown
- 一共有 30 篇系列文章
- 每篇有標題、日期、章節等 metadata
- 要有系列目錄、上下篇和閱讀進度
- 要有 RSS
- 要處理 Sitemap 和 SEO
- 最後部署到 GitHub Pages

這個網站最主要的事情，就是把已經寫好的內容整理成適合閱讀的網頁。

使用者進來之後，主要是在看文章、切上一篇下一篇、看系列目錄。

網站有一些互動，重心還是在內容。

這時再回頭看 Astro，我就比較能理解為什麼它會被排在前面。

用 Vue 一樣可以把網站做出來，只是這類內容網站需要的很多事情，要再自己組合處理。

Astro 本來就很適合拿來做這類內容網站。Markdown 可以直接當內容來源，頁面可以在網站建置時產生靜態 HTML，也有 RSS、SEO 和靜態部署這些內容網站常見的做法。

我目前不懂這些功能底下到底怎麼實作，但至少我看得懂一件事：

**它很擅長的事情，剛好就是我現在要做的事情。**

## 這跟我其他 Web App 的需求不太一樣

我其他用 Vue / Vite 的 Web App，做的事情通常很不同。

像是：

- 很多表單和操作
- 要跟 API 互動
- 畫面狀態持續改變
- 有工作流程要一步一步推進

這些產品裡，使用者會一直跟系統互動，前端也要一直處理目前狀態。

所以我現在會先問一個更前面的問題：

**這個產品主要到底在做什麼？**

是把內容整理好給人看，還是讓使用者一直操作、修改資料、推進流程？

這種層級的差異，是我目前比較有辦法參與判斷的地方。

## 我現在大概是這樣參與 AI 的技術選型

整理這次經驗之後，我現在的做法大概是：

先把我要做的東西講清楚。

再讓 AI 提幾個候選方案。

接著請 AI 用我聽得懂的方式講每個方案適合什麼、優缺點在哪、有哪些限制。

如果裡面出現我以前碰過的技術，我也會繼續問：那為什麼不用這個？用了會多哪些工作？換成另一個方案又會有哪些差別？

最後，我再把這些理由拿回來跟自己的需求對。

我目前比較能判斷的是：

**AI 給我的這些理由，有沒有真的回答我現在要解的問題？**

至於 AI 對框架底層的解釋是不是完全正確，或長期還有哪些我沒看到的取捨，這一層我目前還判斷不到。

## 後來做技術部落格時，我又碰到一次

後來我要做現在這個技術部落格「雞蛋糕的開發筆記」時，也重新比較過候選框架。

因為網站寫作預計沿用鐵人賽時的工作流程，內容主體一樣還是 Markdown 文章，所以最後還是用 Astro。

但這次有些地方需要更多互動，就再加入 Vue islands，也就是只在需要互動的局部使用 Vue。

這次我又多理解一件事：技術選型不一定代表整個網站只能選一個框架，不同部分有不同需求，也可以讓不同技術各自負責。

## 我還不會完整的技術選型

我現在還不能說自己會完整做技術選型。

像框架底層實作、執行方式、效能差異、生態系，還有大型 codebase 的長期維護成本，這些我都還沒有能力自己判斷。

我目前能做的是先把產品問題講清楚，知道內容和資料從哪裡來、使用者會怎麼用、系統大概要負責什麼，再要求 AI 提出候選方案，把差異和取捨解釋到我能理解的程度。

當程式主要由 AI 寫，我還不能靠框架實作細節完成技術選型，但也不需要連「為什麼選這個框架」都一起交給 AI。

至少現在，我可以先判斷這個選擇和我要解決的問題有沒有對上。
