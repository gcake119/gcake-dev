**鐵人賽正式開賽後，我一邊修正自動發文遇到的問題，也持續和 Codex 討論：這些修改要怎麼整理，才能讓其他人也能使用？**

因為我從一開始就希望，這份專案除了用來發布自己的 30 篇文章，也能讓別人 fork（複製一份完整專案到自己的 GitHub 帳號），換成自己的內容和設定後，照著文件自行操作，或交給 AI Agent 協助建立同樣的網站、自動發文與通知流程。

我沒有另外維護空白模板，公開的 repo 就包含自己的 30 篇正式文章、網站設定和發布工具。

## 每天自動發文的流程，怎麼一起整理進模板？

正式開賽後，我遇過明明已經登入 iThome，自動發文工具卻連到另一個沒有登入的 Chrome。整理這部分的模板時，也需要把專用瀏覽器的設定與連線方式寫清楚，讓下一個使用者能照著操作，同時保護自己的登入資料。

每天定時執行的腳本與排程，則要提供可以自行填寫電腦路徑的範例，以及安裝和檢查方法。

實際發文時，還遇過 iThome 的反自動化機制阻擋，最後需要手動補發文章。文章公開後，也曾發生監控工具無法正確辨識結果，仍然透過 Hermes 發出異常通知。在處理這些問題的過程中，停止自動操作、人工接手與公開驗證的規則也持續補強，相關程式和 Hermes 提示詞則一起整理進專案。

從登入、定時發文到結果監控，這些修正逐步成為模板的一部分。可以共用的程式、腳本範例與操作規則保留在 repo，個人的登入資料、Telegram 連線資訊與私人運行紀錄則留在各自的環境裡。

## 整套流程也要能分開啟用

雖然我自己把網站、自動發文和通知串在一起使用，其他人可能只需要其中一部分。

文章網站可以獨立使用。想要自動發文，再設定本機發布工具；需要 Telegram 通知，再啟用 Hermes。

延伸閱讀也是選配，可以把文章放在同一個網站、連到外部網站，或完全不啟用。

而且功能留在專案裡，不代表它已經開始運作。例如有自動發文程式，還需要完成登入、安裝排程與實際測試。

因此，後來把網站部署、自動發文、通知和其他排程分成不同的設定階段，各自說明操作方式與完成條件。

## 交給 AI Agent，也要能照步驟接手

這份 repo 已經包含我的正式文章和設定。其他人 fork 之後，Agent 會看到這些現成資料，因此初始化時必須先詢問使用者的帳號、系列名稱、日期和 GitHub 專案資訊，不能直接沿用原本的內容。

為了避免 Agent 直接覆蓋現有設定，後來把初始化整理成一套需要使用者同意、完成後也會執行檢查的流程：

```text
收集必要資料
→ 預覽設定
→ 使用者確認
→ 寫入設定
→ 檢查結果
→ 執行測試與建置
```

完成基本設定後，如果要繼續部署網站、登入 iThome、建立草稿或安裝排程，還需要使用者另外授權。

每個階段也有自己的驗收方式。例如本機成功產生網站，還需要打開 GitHub Pages 的公開網址，查看文章、圖片和連結是否正常，才能判斷部署是否完成。

把設定順序、授權範圍與完成條件寫進文件，下一個使用者就可以自行操作，或交給 AI Agent 協助完成，不需要知道我之前和 Codex 討論過哪些細節。

## 從可以 fork，到真的能接手

開賽後實際運行這套工具，讓我持續補上腳本範例、設定文件、Agent 操作流程，以及遇到異常時的處理規則。這些都是下一個使用者要接手整套流程時，需要知道的事情。

**從「可以 fork」到「真的能接手」，我還在持續把自己實際使用時需要的設定方式、處理規則與驗收方法，整理成下一個使用者也能照著完成的流程。**
