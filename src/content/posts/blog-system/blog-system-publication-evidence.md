# 讓自動發文不只會執行，也能正確回報結果

前面已經替技術部落格建立固定的發文規則，也安排了跨平台同步流程。文章可以依照排程在自己的網站公開，也能透過自動化流程發布到 Substack。

發文流程自動化之後，我還需要確認文章是否真的公開，以及發生問題時該如何處理。

因此，我讓 Hermes 協助監控發文狀態。它每小時檢查文章排程、網站 RSS、公開頁面與 Substack 的發布狀態。平常保持安靜，確認新文章公開、發布逾期或異常恢復時，才透過 Telegram 通知我。

實際使用後，我遇到幾個需要改善的問題。

## 收到異常通知，卻不知道哪裡出了問題

有些 Telegram 異常通知只能知道系統偵測到問題，卻看不出是哪個環節出了狀況。

一篇文章從排程到公開，需要經過 GitHub 保存文章、GitHub Actions 執行工作、網站部署，以及 Substack 同步等環節。

遇到這種通知，我會請 Codex 從相關執行紀錄與發布狀態著手，確認哪些工作已完成、哪些結果仍待查證，再找出可能出問題的環節。

這讓我發現，通知需要指出目前掌握的問題範圍，才能協助判斷下一步。例如發布延遲時，需要找出尚未完成的環節；暫時無法讀取網站時，則需要先重新查證。

## 文章補發成功，通知時間卻不正確

另一個實際遇到的問題，是文章延後補發成功後，Telegram 仍顯示原本預定的發布時間，讓人誤以為文章準時公開。

我請 Codex 對照發文紀錄與 Hermes 的通知邏輯，找出時間資訊的來源，再調整通知使用的欄位與顯示方式。這個過程也釐清了三種時間：

- **預定發布時間**：原本安排文章公開的時間。
- **公開確認時間**：監控成功確認文章已經可以閱讀的時間。
- **通知發送時間**：結果傳送到 Telegram 的時間。

假設文章原定上午七點發布，監控直到九點才成功確認公開。這只能證明九點檢查時文章已經可以閱讀，無法確定文章究竟從什麼時候開始公開。

因此，後來調整通知內容，分別標示原定發布時間與公開確認時間，避免將監控取得證據的時間誤當成實際公開時間。

## 執行結果不明時，不能直接重新操作

除了正確顯示已知結果，系統還需要處理無法確認的情況。

例如，操作 Substack 發布文章時，如果瀏覽器逾時，可能是操作沒有完成，也可能已經成功發布，只是系統沒有收到回應。直接重試，就可能重複建立文章或寄送電子郵件。

為了避免重複操作，發布流程會保存原本的操作紀錄與文章識別資料。遇到結果不明時，先核對既有文章的狀態，再決定是否繼續。

**因此，通知也需要清楚區分「已確認失敗」與「結果未知」，讓我知道接下來該評估是否重試，還是先查證原本的結果。**

## 收到通知後，知道下一步怎麼做

現在我希望收到通知時，能知道文章是否已經確認公開、問題可能在哪個環節，以及是否需要人工處理。遇到結果不明的情況，就先查證，不急著重新執行。

目前仍有部分異常需要請 Codex 協助追查，但至少我已經有更明確的方向：**通知不只要告訴我發生了什麼，還要提供足夠的資訊，讓我知道下一步該怎麼做。**
