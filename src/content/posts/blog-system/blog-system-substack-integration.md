# 想讓文章被更多人看見，我怎麼處理跨平台發文？

建立自己的技術部落格後，我希望文章有更多機會被讀者看見，也想提供電子報訂閱功能，讓讀者可以直接收到新文章。

如果要自行建立內容推薦與電子報服務，還需要額外開發和維護訂閱管理、郵件寄送等功能。

因此，我決定利用現有的內容平台提供這些服務，再透過自動化流程同步文章。接下來，我需要決定使用哪些平台，以及如何讓文章自動同步。

## 從自己的網站，延伸到 Substack

我的技術部落格以系列文章為主，使用 Markdown 撰寫並保存在 GitHub，讀者可以直接閱讀，也可以透過 RSS 訂閱更新。

文章仍由自己的網站管理，接下來要決定的是，哪些外部平台值得增加一條同步流程。

最初規劃時，我考慮讓 Paragraph 和 Substack 並行。Paragraph 最吸引我的是它與 Arweave 的整合。Arweave 是一種以長期保存資料為目標的去中心化儲存網路，我希望能為已發表的文章增加一種長期保存方式。

但後來確認功能時，發現相關官方文件連結已經失效，無法確認 Arweave 發布功能是否仍受到支援。考量繼續使用 Paragraph 就需要多維護一條同步流程，我決定移除 Paragraph，只保留同樣提供電子報服務、也具有內容推薦機制的 Substack。

選擇 Substack 後，還需要決定文章要如何同步。

我原本希望搜尋引擎能將自己的網站視為正式原文，因此想設定 canonical，也就是用來告訴搜尋引擎哪個網址是主要版本的資訊。但實際確認後，Substack 沒有提供符合這項需求的設定方式。

當時考慮過只在 Substack 放摘要，引導讀者回到原站閱讀全文；也可以完整同步，讓讀者直接在 Substack 看完文章。

最後我選擇全文同步，並在正文附上原站連結。這能保留 Substack 上的完整閱讀體驗，但也接受搜尋引擎不一定優先呈現自己網站的限制。文章的正式來源與後續修改仍以 GitHub 為準。

## 沒有發文 API，就沿用鐵人賽的經驗

決定使用 Substack 後，接下來要處理如何自動同步文章。

如果平台提供正式的發文 API，程式就能透過指定介面建立、更新或發布文章。但我請 Codex 蒐集資料後發現，Substack 當時雖然有提供資料讀取功能的官方 API，卻沒有符合需求的正式文章發布 API。

我可以每篇都手動貼到 Substack，也可以讓 AI Agent 操作瀏覽器來完成。因為準備鐵人賽連載時，我已經使用過 Playwright 和 Computer Use 自動發文，因此選擇繼續採用瀏覽器自動化。

Playwright 可以按照預先設定的步驟控制瀏覽器，Computer Use 則能讓 AI Agent 透過畫面操作網站。

鐵人賽期間，我曾使用 Playwright 遇到 Too Many Requests，也就是網站因請求過於頻繁而限制操作的問題。考量這次經驗，我決定優先使用 Computer Use，讓 Codex 操作已登入的 Chrome 後台，處理草稿編輯與發布工作。

Computer Use 仍然依賴瀏覽器登入狀態與網站介面，也無法保證避開平台的自動化限制。

## 瀏覽器自動化也需要維護

實際開發時，除了讓 Codex 能操作 Substack，也需要考慮如何持續執行。

例如，為了避免每次執行都新增 Chrome 分頁，後來調整操作規則，優先重用既有且可以安全操作的分頁。必要時才新增，任務結束後再清理不需要保留的部分。

另一個問題是如何更新既有文章。系統需要保留文章在 Substack 上的識別資料，才能找到原本的草稿繼續編輯，避免每次同步都重新建立文章。

這些都是採用瀏覽器自動化後需要處理的維護工作。因此，我讓 Substack 同步流程獨立運作，外部平台暫時無法使用時，仍能保留 GitHub 中的正式文章，不受同步操作影響。

## 最後，讀者可以怎麼閱讀與訂閱？

透過這樣的安排，讀者可以直接在技術部落格閱讀完整文章，也能使用自己習慣的 RSS 閱讀器追蹤更新，不需要註冊 Substack。如果習慣電子報，則可以透過 Substack 訂閱，或在平台上發現並閱讀文章。

至於 Substack 實際能增加多少曝光或訂閱者，目前仍需要更多使用資料才能判斷。

跨平台發文的方式確定後，下一個需要處理的問題是：**當系統完成發文操作，我要怎麼確認文章真的正確公開，讀者也確實收到該收到的通知？**
