# 從文章網站到編輯後台，我怎麼安排整套系統？

一開始建立技術部落格時，我已經有用 Markdown 寫好的文章，也習慣透過 Git 管理檔案。網站最基本的工作，就是把這些文章整理成方便閱讀的網頁。

後來，隨著編輯後台、圖片管理、自動發布和文章搜尋等功能陸續加入，我開始思考：程式碼應該放在哪裡？不同的資料要怎麼保存？這些功能又該如何一起運作？最後，部落格逐漸形成由 GitHub 與多項 Cloudflare 服務共同組成的架構。

## 程式碼、網站和資料，可以放在不同地方

最初的文章網站使用 Astro 建立，文章以 Markdown 格式保存，和網站程式碼一起放在 GitHub Repository（簡稱 Repo，也就是專案儲存庫）裡。

Git 可以記錄檔案的修改歷史，Astro 則負責將文章轉成網頁，再透過 GitHub Pages 提供讀者瀏覽。

後來增加編輯後台時，我開始需要區分三件事：程式碼放在哪裡、系統在哪裡執行，以及資料存在哪裡。

後台程式碼同樣保存在 GitHub，但操作介面部署在 Cloudflare Pages，後台需要執行的操作則交給 Cloudflare Workers 處理。當我打開文章，Workers 會向 GitHub 讀取檔案；修改完成並正式儲存時，再透過 GitHub API 將變更提交到 Git。

後台提供了一種更方便的操作方式，文章仍然只有一份正式來源。無論是 Codex 修改檔案，或我透過後台編輯，最後都會回到同一個 Repo 管理。

## 圖片和操作紀錄，需要不同的保存方式

文章和程式碼使用 Git 管理很方便，但圖片要怎麼處理，我一開始沒有把握。

我主要擔心的是，隨著文章越來越多，圖片檔案也會持續增加，讓 Repo 佔用太大的空間。因此，我開始了解把圖片放在 GitHub、圖床或雲端儲存服務，各自會怎麼運作。

最後依照 ChatGPT 的建議，採用 Cloudflare R2 保存圖片。

R2 可以理解成專門存放檔案的空間。圖片上傳後，文章只需要記錄圖片網址，讀者開啟文章時再透過網址取得圖片，不必將圖片檔案全部放進 Git。

至於編輯後台需要的資料庫，則是在 Codex 設計系統時提出使用 Cloudflare D1。

D1 用來保存登入資訊、後台操作狀態，以及文章發布過程的紀錄。例如，文章預定何時發布，屬於文章本身的設定，仍然保存在 Git；系統執行發布時產生的狀態、嘗試及錯誤紀錄，則由 D1 管理。

這些資料雖然都和文章有關，用途卻不同。分開管理，可以讓 Git 繼續負責正式內容，其他服務則保存各自需要的資料。

## 文章搜尋也加入了這套架構

隨著文章搜尋功能加入，我除了使用基本的關鍵字搜尋，也增加了能尋找意思相近內容的語意搜尋。

目前使用 Cloudflare Workers AI 的 BGE-M3 模型，把文章內容轉換成代表文字語意的數字資料，也就是向量，再由 Cloudflare Vectorize 保存與檢索。

這些搜尋資料可以根據公開文章重新建立，不需要成為另一份正式文章來源。

模型選擇、索引更新，以及免費額度不足時的處理方式，我會留到後面專門討論文章搜尋的篇章。

## 整套系統的資料怎麼流動？

把這些服務放在一起看，可以依照文章從編輯到被讀者找到的過程，理解整套系統如何運作。

**第一步：編輯與保存文章。**

我透過 ChatGPT 討論並完成文章，再將 Markdown 存入 GitHub；也可以使用編輯後台修改既有文章。後台透過 Cloudflare Workers 讀取 GitHub 的內容，正式儲存時再將變更提交到 Git。如果文章需要圖片，則先上傳到 R2，再把圖片網址放進 Markdown。

**第二步：將文章發布到自己的網站。**

當文章符合發布條件，GitHub Actions 執行建置與部署，由 Astro 讀取 Markdown 產生網頁，再更新 GitHub Pages。讀者開啟文章時，文字來自公開網站，圖片則透過文章中的網址載入。

**第三步：同步外部平台並記錄執行狀態。**

除了自己的網站，部分文章也會透過另一套流程同步到 Substack。

本站是否公開、外部平台是否完成同步，需要分別確認。D1 負責保存發布嘗試、執行狀態及錯誤紀錄，讓後台可以追蹤處理進度。但系統記錄成功，不一定代表讀者已經能在外部平台看到文章，仍需要另外確認實際公開結果。

**第四步：讓讀者搜尋文章。**

公開文章會被整理成關鍵字與語意搜尋索引。讀者輸入查詢時，系統透過這些索引找出相關文章，再將結果呈現出來。

這樣一來，從編輯、保存、發布到搜尋，各個部分都能依照自己的責任使用資料，也能沿著流程理解它們之間的關係。

## 架構安排好，還需要實際驗證

這些服務是隨著不同需求加入的。每增加一項功能，我都需要理解它會使用哪些資料、交給哪個部分處理，以及可能影響原本的哪些流程。

不過，安排好架構，不代表所有選擇都已經驗證過。

例如，當初選擇 R2，主要考慮的是避免圖片佔用太多 Repo 空間，沒有特別想到載入速度。現在實際測試時，我覺得圖片第一次載入偏慢，但還不知道是圖片大小、快取、網路，還是其他原因造成的。

各項服務的長期成本與維護方式，也需要透過後續使用繼續觀察。

另外，當 Codex 和編輯後台都能修改 Git 裡的文章時，還有另一個問題需要處理：要怎麼避免彼此覆寫，確保文章不會被改壞？
