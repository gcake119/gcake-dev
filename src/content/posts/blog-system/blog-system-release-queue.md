# 把自己的發文規則，變成可以自動執行的流程

建立技術部落格時，我希望把寫作和發表分開。先完成文章，再讓系統依照我訂好的規則持續發布。

但這裡有個問題：**當獨立文章和系列連載共用固定發文時間，又允許手動提前發布時，系統該如何決定每次要發布哪一篇？**

為了實現這個需求，系統需要管理文章的發布資格、順序與進度，再依照固定排程執行發文工作。

## 先完成寫作，再決定開始連載

我習慣在系列開始發表之前，先完成所有篇目的寫作。這樣可以在全系列完稿後，再回頭調整文章內容、篇目安排與閱讀順序。

系列全部定稿後，我會再決定是否開始連載。文章內容先準備好，公開時機由我決定，之後固定性的發文工作才交給系統。

## 獨立文章和系列文章，需要不同的發文規則

技術部落格雖然以系列連載為主要形式，但我也會寫一些不屬於任何系列的獨立文章，例如單篇筆記或開發心得。

兩種文章的發布條件有所不同。

**獨立文章只要確認該篇已經定稿，就可以進入自動發布排程。** 如果同時有多篇，依照完成定稿的先後順序安排。

**系列文章則必須全部定稿，並由我另外確認開始連載，才能取得發布資格。** 發表時按照系列清單中的篇目順序進行。

兩種文章共用每週一、週四上午七點的發文時段，每次最多發布一篇。獨立文章優先，系列連載則在下一個可用時段接續。

另外，我也希望保留手動提前發布的彈性。系統必須根據新的進度接續安排，不必由我重新修改後續文章的日期。排程時間到了，如果沒有符合資格的文章，就不發布。

## 固定排程和發布佇列，負責不同的工作

最初的文章網站已經能根據文章設定的狀態與日期決定是否公開。如果只是指定某篇文章的公開日期，這種方式就能處理。但當獨立文章與系列連載共用發文時段，還要允許提前發布或臨時插入文章時，單靠預先設定的日期就不方便了。

因此，發布系統需要兩個部分共同運作。

**排程負責決定什麼時候執行。** 每週一、週四上午七點，系統會在指定時段啟動發文檢查。

**發布佇列負責決定這次要發布什麼。** 可以把它想成一份會隨著實際進度調整的待辦清單。每次排程啟動後，系統會依序處理：

1. **檢查時段**：確認這個時段沒有其他正在執行或已固定的發文工作。
2. **選擇文章**：依照發布資格、優先順序和目前進度，找出下一篇；沒有候選文章就結束這次檢查。
3. **執行並記錄**：再次核對資料，更新文章的發布狀態，並保存執行紀錄供後續接續。

例如，系列第一篇已經發布，第二篇原本預計週四發表，但我在週二就手動提前公開。到了週四，系統便會接著選擇第三篇；如果這時有新的獨立文章符合資格，則先發布獨立文章，系列第三篇順延。

Codex 在設計時，讓 Git 保存正式的文章內容、系列順序與發布設定；Cloudflare D1 則記錄每次發布取得的時段、執行進度及驗證結果。這讓系統能追蹤尚未完成的發布工作，避免重複處理，也不需要我反覆修改後續篇目的日期。

## 讓開始連載的授權真正受到系統保護

在整理這篇文章時，我重新檢查目前的發布系統是否符合原本的需求。

檢查後發現，程式已經能判斷系列是否全部定稿並安排篇目順序，卻缺少獨立的開始連載授權檢查。因此，即使我還沒決定開始公開，系列仍可能自動取得發布資格。

我要求補上這項保護，讓未經授權的新系列不能透過自動排程發布，也不能藉由手動發布繞過授權條件。

這次也補上相關測試，涵蓋未授權系列不得發布、手動提前發文後接續排程，以及沒有候選文章時不建立新的發布工作。修改通過自動化測試、建置與隔離發布演練後，才合併進 GitHub。

目前確認的是程式與測試環境中的行為，後續實際操作仍需要觀察。

這次補上的是原本遺漏的授權條件，也讓我再次確認：即使需求已經說清楚，仍需要檢查實作是否真正符合預期。

## 讓系統執行規則，自己保留決定權

透過這套流程，我可以專注在寫作與發表安排，讓系統負責選擇文章、執行排程與記錄進度，減少每次發文的重複操作。

不過，系統選出文章並開始發布，不代表讀者已經看得到。網站還需要完成建置與部署；同步到其他平台時，也會遇到不同的問題。這些就是接下來要處理的事。
