# 我怎麼替編輯後台設計防呆機制？

替技術部落格增加編輯後台，是為了讓修改文章更方便。但我也需要考慮：如果一次儲存可能覆蓋其他修改，或造成資料不一致，系統該直接完成操作，還是先阻止這次修改？

我的選擇是優先保護資料。因此，在規劃後台時，我主動提出防呆需求，再交由 Codex 設計具體做法。最後整理成三個層次：**儲存前確認版本、儲存時確保資料完整，以及失敗後保留復原的機會。**

## 儲存前：確認文章是否還能安全儲存

假設我在後台開啟一篇文章，準備修改幾個段落。這段時間，Codex 也更新了 GitHub 裡的同一篇文章。如果後台直接儲存手上的舊版本，Codex 剛完成的修改就可能被覆蓋。

為了避免這種情況，Codex 設計了 Git 版本檢查機制。

後台讀取文章時，會取得對應的版本資訊。準備儲存時，再確認 GitHub 中的版本是否已經改變。如果發現衝突，就拒絕這次儲存，避免在我不知情的情況下覆蓋較新的內容。

Git 本身可以保留修改歷史，但事後找回內容仍需要額外處理。透過版本檢查，系統可以在覆蓋發生之前先阻止操作。

即使沒有版本衝突，一次操作如果需要修改多個檔案，仍然要確保它們能完整更新。

## 儲存時：確保相關資料一起更新

例如，修改文章的網址識別名稱時，除了變更文章檔案位置，也可能需要更新系列清單中的文章關聯。

如果文章已經更名，系列清單卻沒有同步更新，就可能造成連結或導覽出錯。

Codex 因此使用 Git 的原子提交機制，讓相關變更一起完成。如果其中一項不符合條件，這次操作就不會產生部分完成的正式提交。

這兩種機制保護了 Git 中的正式資料，但還需要考慮儲存沒有成功時，如何保留我尚未提交的修改。

## 修改失敗後：保留復原的機會

編輯到一半意外關閉網頁，或儲存時才發現版本衝突，都可能讓尚未提交的內容面臨遺失風險。

因此，後台設計了草稿保留與復原機制。

後台的草稿保留機制會記錄修改內容及對應的文章版本。重新開啟文章時，系統可以據此判斷草稿是否適合恢復。如果 GitHub 中的正式內容已經更新，就把舊草稿辨識為可能發生衝突的版本，避免復原時直接覆蓋新內容。

這項機制無法保證任何情況下都不會遺失資料，但能在編輯中斷或儲存失敗後，提供找回修改成果的機會。

## 有保護機制，還需要確認它真的有效

目前這三層保護已有對應的程式實作，部分行為也有自動化測試，例如版本衝突時拒絕儲存，以及相關檔案修改失敗時不留下部分提交。

不過，我目前仍主要透過 ChatGPT Project 完成寫作，尚未大量使用編輯後台。衝突提示是否清楚、草稿能否順利找回，以及發生問題時是否容易處理，都需要後續實際操作才能確認。

## 從操作風險，決定系統應該保證什麼

這次設計編輯後台，我延續了在其他專案中的做法：先從使用情境辨認風險，提出系統需要保證的條件，再交由 Codex 設計具體的工程機制。即使不熟悉底層程式碼，我也需要理解這些保護機制的作用與限制，才能在後續驗證時判斷是否符合原本的需求。
