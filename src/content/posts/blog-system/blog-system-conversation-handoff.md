# 把寫作流程變成 Agent 能接手的固定工作

決定繼續以系列連載整理開發經驗後，我把寫作前後反覆進行的工作，也一起整理下來：企劃與交接文件做成模板，協作步驟寫成規則，連同文章一起放進 Git 管理。

這些檔案集中保存在專案的 Repo，也就是程式碼儲存庫裡。希望每次續寫或開新系列時，Agent 都能依照約定準備資料，定稿後完成交接，減少手動搬檔與重新補充脈絡的工作。

## 每篇文章前後，都有準備與交接

先前在〈我是怎麼跟 ChatGPT 協作寫完 30 篇系列文的〉裡，我整理過鐵人賽的寫作方式：30 篇放在同一個 ChatGPT Project，每篇各開一個對話，從核心問題開始討論，經過大綱、初稿與多輪審稿，最後定稿。

每篇定稿後，還要更新連載進度與銜接紀錄，再手動更新 Project 裡的來源檔案。開下一個對話時，也要交代先讀哪些資料、接著處理什麼。

這些步驟逐漸固定下來，也讓我開始思考：能不能把做法寫清楚，讓 Agent 接手執行？

## 用模板留下下一次需要的資訊

我先把系列企劃與交接紀錄整理成兩份通用模板。

企劃模板幫助新系列開始思考：整個系列要回答什麼問題？有哪些真實經驗可以用？各篇怎麼分工？哪些內容已有舊文可以引用？

交接模板則保存寫作進行中的狀態：本篇確立的論點、已確認的事實、前後篇界線，以及下一篇的起點。

對我的文章來說，還需要持續區分「當時知道什麼、後來才理解什麼、目前仍不知道什麼」。這些資訊會影響學習經驗怎麼敘述，避免下一個對話把後來的理解寫成當時就有的判斷。

模板提供可以沿用的格式，每個系列再建立自己的企劃與交接文件，隨實際討論各自調整。修改共用模板時，也不會直接覆寫其他系列已經確認的內容。

交接紀錄本身同樣需要取捨。如果把完整對話與正文都放進去，下一個對話仍要從大量資料裡找重點。因此，我希望它優先留下會影響後續寫作的決定，需要細節時，再回查正式文章或相關來源。如果交接摘要和正式文章有出入，就回到定稿確認。

## 把讀取與更新的步驟寫成規則

有了模板，還需要說清楚怎麼使用。

我把這些步驟寫進 ChatGPT Project 的指令，也在 Repo 的 `AGENTS.md` 裡保存專案內的協作規則。`AGENTS.md` 是提供給 Agent 閱讀的操作說明。

收到「開始討論下一篇」時，先讀該系列的企劃、最新交接與必要前文，整理核心問題和真實素材，再進入討論。這個階段先確認文章要回答什麼，不直接產生初稿。

等我確認定稿、要求更新 Repo 時，再保存正式文章、更新該系列交接；如果實際內容改變了後續安排，也要調整企劃。

這樣一來，我可以用簡短指令啟動一組已經約定好的工作，不必每次重新列出全部步驟。

其中，Project 指令負責對話中的協作方式，Repo 規則則補上檔案更新與提交時要遵守的要求。兩邊需要配合，也需要分別維護；修改 Repo 裡的指令參考文件，不會自動改變 Project 設定。

## 連寫作方法也一起用 Git 管理

我把會隨寫作持續變動的企劃、交接與正式文章集中放進 Repo，Project 則保留共用寫作規範與學習背景。

Git 會記錄每次修改。之後調整企劃、補充交接欄位或修改協作規則，都可以回頭查看改了什麼，並在修改紀錄中留下原因。

開始工作時，Agent 依規則從 Repo 讀取最新系列文件。定稿後，再更新 Repo 裡的文章與交接文件，省下手動替換 Project 來源檔案的工作。

文章與寫作方法，都能一起保存並持續修改。若發現交接少了一項重要資訊，或某個步驟需要調整，就更新模板與規則，留下變更紀錄，讓這套方法隨使用經驗逐步改進。

## 續寫與開新系列，都有可以接手的步驟

同一系列續寫時，可以從「開始討論下一篇」接續；準備新系列時，則先討論主題與範圍，再沿用模板建立文件。兩種情況都有已經約定好的準備與交接步驟。

我仍然需要提供真實經驗、確認核心問題與論點，並決定文章是否定稿。執行時，也要核對 Agent 讀取的資料與理解是否正確。長期是否容易維護，還需要繼續使用才知道。

固定工作交給 Agent 依規則執行，我把討論時間留給文章真正需要釐清的問題；遇到不順的地方，再調整模板與規則。
