我現在整理 AI 開發流程，最在意的是：每個階段由誰負責，下一個階段接收什麼，以及完成時拿得出什麼證據。

技能裝多之後，很容易出現另一種問題。需求已經寫進規格，協調技能又產生一份計畫；UI 已經選定方向，另一個設計技能又重新訪談；程式才改了一小段，卻接著執行好幾輪完整審查。工具都有用，但分工重疊會消耗時間，也讓真正的完成條件變得模糊。

這套做法結合規格驅動開發（SDD）與測試驅動開發（TDD）。這篇整理我目前採用的架構：**Spectra 管規格與任務，lean-tdd 管測試優先的小循環，設計技能各自負責選定的階段；pstack 與多 Agent 派工依需求加入。**

> 這是持續迭代後，整理於 2026-10-23 的近期版本。文中的觸發範圍與授權限制包含我的本機適配，不代表各套件安裝後的原始預設。UI 的詳細分工另見[〈AI UI 五階段工作流〉](/gcake-dev/posts/ai-ui-five-stage-workflow/)。

## 先分清楚 Skill、MCP 與 Agent

這三個詞常一起出現，但負責的事情不同。

| 名稱 | 白話說明 | 在這套流程中的例子 |
| --- | --- | --- |
| Skill，技能 | 給 Agent 的工作方法與判斷規則 | 如何建立規格、進行 TDD、審查介面 |
| MCP | 讓 Agent 連接工具或資料的介面 | 查詢程式碼圖譜、操作設計服務 |
| Agent，代理 | 實際讀取脈絡、選擇工具並執行工作的角色 | 負責整合的主 Agent，或有明確範圍的 worker |

裝了 Skill，不等於它需要的 MCP 已連線；MCP 可以呼叫，也不代表 Agent 已獲准修改外部資料。工作方法、工具能力與操作授權要分開確認。

## 我的分工架構

下表是責任分工，不是每次都必須跑完的關卡。

| 要處理的問題 | 主要負責者 | 適用邊界 |
| --- | --- | --- |
| 找對 repo、規格與既有決策 | 工作區文件、decision-context | 先確認位置、所有權與既有約束 |
| 理解現有程式 | Codebase Memory MCP、必要時搭配 how | 找程式、呼叫關係與影響範圍；需要完整解釋時才整理成 how 說明 |
| 收斂需求與工程取捨 | spectra-discuss、engineering-design-review | 不清楚才討論；有具體風險或知識缺口才加深審查 |
| 保存規格與工作進度 | Spectra | requirement／spec、Gherkin、tasks 與 change 狀態的主要來源 |
| 決定 UI 方向或改善既有畫面 | 選定的設計技能 | 每個階段一個主責，沿用已核准的產物 |
| 協調較長的工程任務 | pstack，明確選用時 | 沿用現有規格與驗證規則，不另建一套流程 |
| 選擇是否派工 | baton-dispatch，確有需要且已授權時 | 先判斷直接完成是否更省成本 |
| 依規格實作 | spectra-apply | tasks.md 是唯一的任務進度來源 |
| 以測試驅動行為變更 | lean-tdd | 真正的 acceptance RED → GREEN → REFACTOR |
| 驗證與交付 | 專案既有檢查、對應審查與人工驗收 | 依變更影響選擇；提交、發布與清理另依授權處理 |

下圖把工作分成四層：理解與決策、規格與設計、實作與驗證、授權與交付。每層都標示技能責任與階段產出；pstack 放在跨階段的選用協調層，不佔一個必經步驟。前三層依任務推進，交付層則按本次授權分別選擇，不表示一定要依序封存、發布再清理。

pstack 與派工不另外排成兩個必經階段。它們改變的是「如何協調工作」，規格、驗收條件與必要檢查仍沿用同一份基準。

## 一、先找對工作位置，再理解系統

repo（repository）是用來儲存專案內容並管理版本的儲存庫，裡面可以是程式碼，也可以是文件。我有些產品採用多 repo 工作區：

```text
product-workspace/
├── coordination/       跨 repo 規格、介面約定與決策
├── frontend/           前端程式與專屬文件
├── backend/            後端程式與專屬文件
└── document-engine/    其他服務
```

這是我的其中一種安排：最外層只收納專案，各子資料夾才是獨立 Git repo。其他產品可以採 monorepo，不需要為了套用本文而改目錄。

開始前要確認：這次修改在哪些 repo、規格由誰維護、是否已有未提交的工作，以及哪些檢查必須在各 repo 內執行。若專案有工作區目錄工具，就沿用它；沒有時，讀取現有文件也可以，不把特定工具當成啟動條件。

接著用 `decision-context` 讀取相關決策，例如 ADR（架構決策紀錄）、`DESIGN.md`、Spectra 現行規格及歷史變更。跨 repo 的共同約定放在協作文件中，單一 repo 的內部細節留在該 repo，避免維護兩份互相漂移的正式規格。

在我的環境中，程式探索優先使用 [Codebase Memory MCP](https://github.com/DeusData/codebase-memory-mcp)：先找相關符號、呼叫鏈與資料流，再閱讀實際程式。若沒有索引，依任務授權建立本機衍生索引；若能力受限，就如實說明，不把「找不到圖譜」誤認成「沒有這段程式」。

`how` 則用來把調查結果整理成人能理解的系統說明。單純修一個已定位的欄位，不需要每次都重新寫一份架構介紹。

## 二、需求不清楚才討論，工程審查回答具體問題

`spectra-discuss` 負責收斂產品問題：誰遇到什麼困難、預期看見什麼結果、這次做哪些範圍，以及怎樣才算完成。討論階段不因為順手就開始實作。

`engineering-design-review` 處理工程上的盲點，例如重試是否造成重複寫入、快取何時失效、資料同步失敗後如何恢復，以及新舊版本如何相容。

兩者可以接續使用，但不需要對每個小修改都執行完整審查。若問題只是一個既有規則下的文案修正，直接依目前脈絡完成即可；若要更換跨服務同步機制，就值得先把失敗情境與取捨說清楚。

可用的提示詞：

```text
先確認既有決策與這次需求，找出會影響驗收的未決問題。
如果需求已經足夠清楚，直接沿用，不重新訪談。
只針對可能改變實作方向的工程風險提出選項與證據。
這階段先不實作，也不做外部寫入。
```

## 三、Spectra 管規格，Gherkin 必須先於 tasks

我使用 [Spectra](https://github.com/kaochenlong/spectra-app) 保存 change proposal、規格、工程設計與任務。我的適配額外要求：重要需求的驗收情境要在產生 tasks 前完成。

順序是：

1. 建立或沿用 requirement／spec，說明需要的行為。
2. 補上正常流程、重要失敗流程與必要邊界的 Given／When／Then。
3. 需要工程設計時補上 design；若 UI 或共享契約仍未定案，先收斂，必要時同步更新規格。
4. 驗收方式足夠明確後，再建立可執行的 tasks。

Gherkin 是把驗收情境寫成具體條件與結果的方法。例如一個只有兩個名額的預約檢查：

```gherkin
Scenario: 剛好使用全部名額
  Given 目前有兩個名額
  When 使用者申請兩個名額
  Then 系統接受申請，並顯示剩餘零個名額

Scenario: 名額不足
  Given 目前有兩個名額
  When 使用者申請三個名額
  Then 系統拒絕申請，並維持兩個剩餘名額
```

情境描述使用者或其他系統能觀察到的結果，不把 class、function 或資料庫欄位塞進驗收條件。實作可以改，對使用者的承諾不應跟著被悄悄換掉。產品行為需要調整時，先取得釐清或確認，再同步更新 spec、Gherkin 與受影響的 tasks。

在目前的文件慣例中，spec 使用英文規範語句；proposal、design、tasks 依專案設定使用繁體中文。程式識別字與指令維持原樣。

`tasks.md` 是工作進度的唯一來源。Agent 可以留下執行紀錄，但紀錄不是另一份正式計畫。若實作時發現驗收條件矛盾或缺漏，要先釐清，不能直接修改條件讓測試通過。

提案完成後，我的 `spectra-propose` 會 park，也就是暫存這份 change，保留規格供後續使用。單純要求提案不等於要求實作；若同一次任務已明確授權完整開發，就可在完成提案階段後接續原定的 apply，不重複詢問已授權的範圍。

## 四、新專案初始化，也要避免多出一套技能

在持續調整技能採用架構的過程中，我也把 Spectra 初始化納入管理：初始化會產生專案內的技能。若全域已經有同名的使用者適配版，就可能同時出現兩個入口。

因此，我把初始化重用規則接到 Spectra 相關技能，pstack 也引用同一份規則。**即使沒有啟用 pstack，新專案也能沿用既有技能。**

處理方式是先盤點，再初始化與比對：

- 專案已初始化、沒有要求更新，就不再跑一次 init。
- 新生成的同名技能，先確認既有版本能載入、用途與目前 CLI 能力適用。
- 確認可重用後，完整備份並驗證新產物，再只移出這次新生成的冗餘入口。
- 沒有既有對應的技能、原本就存在的客製內容，以及尚未釐清的差異都保留。

同名不是功能完全相同的證據。這套規則也不會在讀取狀態、討論需求或查詢文件時，自動取得初始化、更新或刪除權限。

這是 Agent 遵循的工作規則，沒有修改 Spectra CLI。直接在終端執行 init，仍會產生工具原本會生成的檔案。

## 五、pstack 是選用的協調層

[pstack](https://github.com/cursor/plugins/tree/main/pstack) 提供工程工作方法。我在本機採用適配版，讓它接到既有 Spectra、TDD、設計分工與授權規則。

我的使用方式是明確選用：需要 pstack 協調某個任務時才加入，安裝本身不會開啟常駐模式或排程。

它在這裡負責選擇適當的工作方法、控制範圍、整理交接與證據。已經有 Spectra change，就沿用；已經有設計稿，就交給原本的設計負責者；需要 TDD 時，pstack 的 `tdd` 只轉接一次既有 `lean-tdd`。

我也取消了適配版中不適用的必做預設，例如每次都開 PR、固定數量的平行驗證、另裝清理插件或先刪除註解。是否增加檢查，要能說明具體風險、目前缺口與維護成本。

```text
請用 pstack 協調這次修正，沿用現有 Spectra change 與 tasks。
TDD 使用既有 lean-tdd，UI 沿用已核准設計，不另開完整流程。
完成受影響專案的本機驗證後回報證據。
這次不 commit、push、開 PR、部署或清理其他工作目錄。
```

若任務很小，直接用 Spectra 與對應技能就可以，少一層協調通常更清楚。

## 六、設計先收斂，派工再決定

UI 並不是每個功能都要重新設計。既有表單修正通常直接沿用元件與 tokens；全新頁面沒有方向，才需要視覺探索。

我的原則是每個階段一個主責：Product Design 可以負責視覺方案與選定來源的原型；Impeccable 負責既有 UI 的局部改善；Hallmark 是明確選用的品牌視覺方案；UI/UX Pro Max 只補具體的參考缺口。詳細選擇方式放在[另一篇 UI 工作流](/gcake-dev/posts/ai-ui-five-stage-workflow/)。

若明確選擇透過 OpenDesign Cloud 完成設計交付，才使用 `open-design-delivery`。它需要對應服務可用，並保存明確核准的設計來源與版本，再交給 Local Codex 實作及驗證。其他流程已經核准的設計，不需要為了補一個步驟而重做一次。

派工也是如此。`baton-dispatch` 先判斷直接完成是否更划算；只有工作能安全拆分、收益高於協調成本，而且委派已獲授權，才增加 workers。

| 工作狀況 | 我的選擇 |
| --- | --- |
| 小型、緊密耦合修改 | 主 Agent 直接完成 |
| 有界線的調查，另一份脈絡有幫助 | 視授權使用一個唯讀 worker |
| 可獨立推進、不重疊寫入的工作 | 少量平行 workers |
| 多個方案會修改相同區域 | 有需要才建立隔離工作區 |
| 共享契約仍不穩定 | 先收斂，不急著派工 |

worker brief 要說清楚目標、所有權、可修改範圍、驗證方式與停止條件。主 Agent 仍負責整合與最終判斷。平台不支援或未授權委派時，就循序完成，不把自行重讀冒稱獨立審查。

## 七、行為變更從真正失敗的 acceptance test 開始

Acceptance test 是驗收測試，檢查約定的行為。它可以是單元層級、整合介面或 CLI 測試，不一定要透過瀏覽器跑一整條 E2E。

我的 `lean-tdd` 從穩定的公開介面切入：

1. **RED**：從 Gherkin 寫出最小行為測試，執行並確認它因為預期的行為缺口而失敗。
2. **GREEN**：實作剛好能讓測試通過的修改。
3. **REFACTOR**：維持綠燈，整理結構，不順便加入新行為。

檔案不存在、套件沒裝好或測試語法錯誤，不是有效的行為 RED。修 bug 時，第一個失敗測試要能重現該問題；若只是替已經正常的行為補測試，就先記錄現況，再以暫時突變確認測試能抓到破壞，之後立即還原。

小修改、時間壓力或測試較難，都不是默默跳過 RED 的理由。純文件與格式調整則不必為了形式，硬造一層無法證明行為的測試。

測試層級選擇成本最低、足以覆蓋風險的方式。邏輯用單元測試，系統邊界用整合或契約測試，瀏覽器互動與重要旅程再用 E2E；不把每個情境在所有層重寫一遍。

## 八、把驗證階段分清楚，避免重跑卻沒有增加證據

CI 是持續整合，會在指定環境執行自動檢查；PR 是提交給專案審閱與合併的變更請求。它們各有用途，不代表產品的所有驗收都已完成。

| 階段 | 要回答的問題 |
| --- | --- |
| TDD 小循環 | 這次行為缺口是否已修正？ |
| 本機完整必要檢查 | 受影響專案要求的檢查是否都通過？ |
| PR CI | 在乾淨的線上環境，是否符合合併條件？ |
| 部署後 Smoke Test | 指定環境的基本功能是否可用？ |
| 人工驗收 | 使用者是否接受實際產品結果？ |

這些證據用途不同。編譯成功不代表互動正常，本機通過不代表已部署，CI 綠燈也不等於真人已接受。

開發時跑單項檢查縮短迴圈；推送新候選版本前，完成受影響專案要求的完整本機驗證。若 aggregate 指令已包含 typecheck 與單元測試，就不為了報告再各跑一次。

CI 失敗時，先讀 log、回本機重現、定位並修正，不把反覆 push 當成試錯方式。只有在線上才能重現時，要說清楚原因、本機做過什麼，以及尚未確認的限制。

審查也依問題選用。一般 diff 使用一般 code review；懷疑設計漂移時用 `design-and-standards-review`；具體安全風險交給合適的安全審查；UI 則在真實畫面確認互動、狀態與核准設計。不同檢查涵蓋同一風險時，優先重用有效證據，不固定再加一輪「第二視角」。

重用證據前，要確認被測程式（包括未提交修改）、相依套件、設定與相關環境仍一致，而且原檢查確實涵蓋當前風險。

## 九、封存、提交、發布與清理，都看本次授權

功能驗證完成後，先回報做了什麼、哪些檢查通過、還有哪些缺口，以及是否需要人工驗收。接著依本次任務授權處理：

- `spectra-archive`：封存完成的 change，依實際預覽與操作結果套用 delta specs，不能跳過驗證或自動勾掉未完成項目。
- `decision-context`：把值得長期保留的決策補回文件，不為每次小修新增 ADR。
- `spectra-commit`：只提交特定 change 所屬的變更；`lazy-commit`：分析未提交的內容，依目的拆成 atomic commits。兩者都在已有提交授權時使用，選擇適合的一個入口，不重複提交。
- push、PR、merge、部署、對外留言與排程：依本次明確範圍執行，不從「自主完成」推導出全部權限。
- worktree 與測試環境清理：保留其他工作、未提交修改、資料與驗收證據，只精準處理有授權的範圍。

這些操作不必固定全部執行，也沒有對所有專案都適用的封存與提交順序。已獲授權的工作繼續做，不反覆詢問；尚未授權的外部效果，則停在可審查的成果。

## 讓工作流跟著實務持續迭代

這是我持續整理需求、規格、設計、實作與驗證分工後，最近期採用的版本。這一輪調整的重點，是讓原本各自有用的技能能接得起來：共用規格與初始化規則、保留已核准的設計、減少重複啟動，並把交付授權與驗收證據說清楚。

後續加入新技能或更新版本時，我也會用相同原則判斷：它補上了哪個具體缺口？要接到哪個既有階段？能否沿用已經完成的工作？原本的規格、客製內容與授權界線是否仍然成立？

我現在選擇技能時，會先問三件事：這個階段已經有誰負責？這次要增加的工具能補哪個缺口？完成後要留下什麼可以核對的結果？答案清楚時，再加入工具，流程通常更容易維護。
