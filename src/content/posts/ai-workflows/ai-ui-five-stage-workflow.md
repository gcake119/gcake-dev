我以前會把 UI 工具排成一條長鏈：先探索、再產生設計系統、接著做原型、最後讓幾個技能輪流評審。看起來很完整，實際使用卻容易重複問需求、重做已選好的方向，甚至得到兩份互相衝突的設計規則。

現在我的流程保留五個階段：**判斷任務與主責、收斂設計方向、固定設計契約、實作與局部精修、驗證畫面與行為。** 每個階段選一個主責，其他工具只有在能補上具體缺口時才加入。

五階段是方便理解工作的架構，不代表修改一個按鈕也要從第一階段全部重跑。已經有核准設計的任務，可以直接從實作開始。

> 這是持續迭代後，整理於 2026-10-23 的近期版本。以下是我的本機技能分工，部分觸發描述經過適配，不代表各工具上游的完整能力或原始預設。完整工程流程另見[〈AI Agent 協作開發工作流〉](/gcake-dev/posts/ai-agent-development-workflow/)。

## 先看懂五組技能的分工

| 技能／插件 | 在我目前設定中的角色 | 不會因此自動啟動的工作 |
| --- | --- | --- |
| frontend-design | 當新介面或重大改版沒有視覺方向時，選擇一個設計流程 | 它本身不產生設計、不實作，也不串接所有工具 |
| Product Design | 視覺方案探索、選定圖片／網址的忠實原型，以及以畫面與操作旅程為主的 UX 評審 | 不接管一般既有 UI 小修，也不把每張 bug 截圖當成重建需求 |
| Hallmark | 使用者明確選擇時，進行品牌美術方向、設計語彙分析、audit 或 redesign | 不預設接在 Product Design 後面再做一次完整探索 |
| Impeccable | 既有介面的版面、文字、狀態、響應式與可及性改善，使用對應的局部指令 | 一般「幫我改善」不等於執行完整 craft 流程 |
| UI/UX Pro Max | 按需要查配色、字體、圖表、互動模式或實際技術堆疊的參考 | 不對每個 UI 任務重建一套 design system |

這些是責任邊界，不是能力排名。例如 Impeccable 上游也能從零設計，但在我的設定裡，新視覺探索通常交給已選定的 Product Design 或 Hallmark，讓同一個階段有清楚的主責。[Impeccable 官方介紹](https://impeccable.style/)說明了它更廣的設計能力。

當某個主責流程需要內部 QA 或一次參考查詢時，可以使用輔助工具。關鍵在於它們沒有重新開一份 brief、再選一次方向，或建立第二份正式設計系統。

## 五階段總覽

| 階段 | 核心問題 | 常見主責 | 交給下一階段的內容 |
| --- | --- | --- | --- |
| 一、判斷任務與主責 | 是探索新方向、忠實還原，還是修正既有介面？ | 必要時由 frontend-design 分流；明確指定時直接進對應技能 | 任務範圍與主責 |
| 二、收斂設計方向 | 使用者要採用哪一種可見的方案？ | Product Design，或明確選用的 Hallmark | 選定設計、假設與尚未解決的問題 |
| 三、固定設計契約 | 實作要遵守什麼，哪些狀態需要驗收？ | 目前設計主責；按來源使用 DESIGN.md、Stitch 或既有文件 | 核准來源、tokens、狀態與驗收條件 |
| 四、實作與局部精修 | 如何依專案技術把已選方案做出來？ | 原專案實作流程、對應元件技能；局部改善用 Impeccable | 真實可執行的介面與測試證據 |
| 五、驗證畫面與行為 | 畫面、互動、程式與使用者預期是否一致？ | 依風險選擇 UX、技術審查與真實瀏覽器驗證 | 已確認結果、待修問題與人工驗收狀態 |

## 第一階段：判斷任務與主責

UI 任務最容易混淆的地方，是把「沒有方向」與「已經知道要改哪裡」當成同一種需求。

我現在先分類：

| 實際需求 | 選擇方式 |
| --- | --- |
| 新產品沒有畫面方向 | 由 frontend-design 選擇一個探索流程 |
| 已指定 Product Design、Hallmark 或某個局部指令 | 尊重指定，直接交給對應主責 |
| 已有選定的圖片、網址或設計稿，要忠實做成原型 | 需要時直接使用 Product Design 的對應還原流程 |
| 既有表單排版擠、錯誤狀態不清楚或手機版跑掉 | 使用對應的 Impeccable 工作，不重新探索整站 |
| 只有圖表、字體或框架細節不確定 | 按需查 UI/UX Pro Max，原主責繼續負責結果 |

`frontend-design` 在我這裡是分流入口。它選定主責後就交接，不會因為任務叫做 redesign，就把 Product Design、Hallmark、UI/UX Pro Max 全部跑過一遍。

我也會區分「以某個網站為靈感」與「忠實還原該網站」。前者仍要確認自己的產品、內容和方向；後者需要明確的來源與還原範圍。貼一張截圖回報按鈕跑版，更不等於授權重建整個頁面。

提示詞可以直接說明：

```text
這是既有表單的手機版排版問題，請使用 Impeccable 的局部改善方式。
保留功能、資訊架構與現有設計 tokens，只修這個範圍。
不要重新做視覺探索，也不要產生第二份設計系統。
```

## 第二階段：收斂設計方向

全新介面需要探索時，Product Design 可以負責產生視覺方案，讓人先看到畫面，再選擇方向。它也能處理選定來源的原型，以及從實際畫面檢查產品操作旅程。

brief 是產品摘要，包含目標、使用者與限制。這個階段的輸入不必是一大份訪談。先沿用已有的目標使用者、核心任務、內容與限制，只補會改變設計選擇的缺漏。

可比較的方案應該能看出差異，例如資訊密度、主要操作位置、內容層級與品牌氣質，而不只是換幾個顏色。

```text
請使用 Product Design，根據現有產品 brief 探索這個後台首頁的視覺方向。
主要使用者每天要查找案件與處理例外，請重視掃讀與操作效率。
沿用已確認的功能與內容，提供可比較的畫面方案。
先停在選方向，不串接 Hallmark 或另一個完整設計流程。
```

### 什麼時候改用 Hallmark？

當我明確需要品牌美術方向，或想研究某個參考的排版、字體與色彩語彙時，才選 [Hallmark](https://github.com/nutlope/hallmark)。它是另一個可選主責，不是 Product Design 結束後的固定第二輪。

- `study`：研究參考作品的設計語彙。
- `audit`：檢查指定範圍的設計問題。
- `redesign`：在授權範圍內重新設計，保留約定的內容與功能邊界。

以下是給 Agent 的自然語言提示，不是要求在終端直接執行同名命令：

```text
這次明確使用 Hallmark study，分析參考頁面的字體、色彩與內容節奏。
先輸出可用於我們品牌的判斷，不直接重建網站。
若要進一步 redesign，先列出範圍與需要確認的設計決策。
```

### UI/UX Pro Max 如何補位？

[UI/UX Pro Max](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill) 在我的設定中是一個可查詢的設計參考來源，支援依實際 Web 或原生應用的技術堆疊找資料。

例如目前的主責已選定版面，但還不確定長時間閱讀的字體搭配，或某組資料適合哪種圖表，就問這個具體問題。查完後仍回到原設計，不把資料庫預設覆蓋核准內容。

```text
請使用 UI/UX Pro Max，只查適合這組資料的圖表形式與可及性注意事項。
專案是 Vue，已有 DESIGN.md；不要重新產生整套設計系統。
將建議交回目前的設計主責整合。
```

若沒有這類缺口，就跳過。工具收錄多少方案會隨版本變動，我更在意查詢能否幫助眼前的決策。

## 第三階段：固定設計契約

畫面選好了，下一步是讓人與 Agent 知道實作要遵守什麼。

我會保留設計來源或版本、適用頁面、主要狀態、響應式行為，以及誰在何時核准。需要長期沿用的設計語言，才整理進 `DESIGN.md`；若既有 tokens、元件與文件已足以交接，就直接沿用。文件中的色彩與間距等實際值，也要與程式中的 tokens 對得起來。

tokens 是程式中可重用的設計值，例如語意色彩、字級與間距。`DESIGN.md` 是設計規則，Spectra 是行為規格，設計稿是可見的參考來源。三者要互相對應，不各自長出另一套需求。

| 已有的設計來源 | 如何延續 |
| --- | --- |
| 專案已有 DESIGN.md 與 tokens | 直接沿用，只補本次缺少的決策 |
| Product Design 的選定方案 | 保留原始目標與選定版本，交給後續實作 |
| Google Stitch 設計 | 依需要使用 design-md 與相關 Stitch 技能整理設計語言 |
| 已有前端程式，但缺少設計規則文件 | 必要時用 stitch::extract-design-md 從現況整理，不先重新設計 |
| 明確選用 OpenDesign Cloud 的設計交付 | 由 open-design-delivery 保存核准來源，再交給 Local Codex 實作 |

[Stitch Skills](https://github.com/google-labs-code/stitch-skills) 提供與 Stitch 設計工作相關的能力；在我的流程中，它們依實際設計來源選用，不是每一份圖都必須先送進 Stitch。

`open-design-delivery` 也有明確適用條件：需求與驗收已足以進入交付，但 UI 尚未定案，而且這次選用 OpenDesign Cloud。服務不可用時先處理能力缺口，不自行換成另一套完整流程。

如果 Product Design 或其他工具已經完成設計核准，就不需要為了「保存設計」再跑一次完整設計工作。

可互動的原型用來確認設計與流程，不表示正式後端、資料處理與權限都已完成。進入實作時，仍要依 Spectra 的行為契約接回專案，分別驗證。

設計核准也不等於核准所有產品行為。例如刪除資料、調整權限或改變審核規則，仍要回到 Spectra 的正常、失敗與邊界 Gherkin。這些驗收情境要先於相關實作 tasks 完成。已有 tasks 時，先釐清並確認設計是否改變了產品行為，再同步更新 spec、Gherkin 與受影響的 tasks；不為了符合圖片而自行改寫驗收條件。

## 第四階段：實作與局部精修

有了選定設計，才開始把畫面落到專案中。

第一件事是讀現有框架、元件系統、alias、tokens 與附近模式。我的選擇是：

| 專案現況 | 使用方式 |
| --- | --- |
| React 專案已採 shadcn/ui | 使用 shadcn 技能讀取設定並沿用現有元件 |
| Vue 專案已採 shadcn-vue | 使用 shadcn-vue 技能，遵循既有元件與樣式慣例 |
| 已使用其他元件庫或自建設計系統 | 繼續使用，不為了套技能而更換整套技術 |
| 原生應用 | 按實際平台實作，必要時查對應參考，不套用 Web 專屬假設 |

[shadcn 官方技能文件](https://ui.shadcn.com/docs/skills) 可用來了解其專案整合方式；是否採用元件庫，仍由產品與現有技術決定。

表單驗證、權限、非同步錯誤與重要互動，回到 Spectra／lean-tdd 的行為測試流程。不要只測原始碼是否包含某個 class，也不要為每個單一畫面的間距新增一整套 E2E。

```text
依核准設計與既有 DESIGN.md 實作這個表單。
先讀專案元件與 tokens；已有元件就沿用，不更換元件庫。
行為變更依 Spectra Gherkin 先取得 acceptance RED，再完成實作。
回報實際畫面與互動證據，不以編譯通過代替驗收。
```

### Impeccable 不必等到最後才使用

既有頁面的局部改善可以直接使用 Impeccable，也可以在依核准設計實作時，處理一個明確的細節問題。

| 具體問題 | 對應的局部工作例子 |
| --- | --- |
| 間距、對齊與內容節奏 | layout |
| 提示文字、標籤與錯誤訊息 | clarify |
| 不同尺寸的排版 | adapt |
| 長字串、錯誤與邊界狀態 | harden |
| 最後的細部一致性 | polish |
| 程式層可及性、效能或響應式問題 | audit |

實際指令名稱與使用方式依已安裝版本確認。明確要求 `craft` 才進入完整流程；一句「幫我改善這張表單」不會自動觸發整套訪談與視覺重做。

```text
請使用 Impeccable layout 修正這個案件列表。
沿用核准方向，只處理資訊層級、間距與窄螢幕排列。
不要新增功能、改寫資料流，或重新產生 DESIGN.md。
完成後在指定尺寸確認沒有內容遮蔽與操作問題。
```

## 第五階段：驗證畫面與行為

UI 驗收不能只看一張好看的截圖，也不需要每次把所有審查技能輪流跑完。

我先問這次缺少哪種證據：

| 要確認的事情 | 合適的方式 |
| --- | --- |
| 使用者看不看得懂、流程能不能順利完成 | Product Design 的畫面／產品旅程 audit，或明確選定的對應評審 |
| 品牌視覺與參考方向是否一致 | 明確選用 Hallmark audit，沿用既有設計來源 |
| 表單標籤、focus、語意、響應式程式問題 | Impeccable audit 或 Web Design Guidelines，依檢查範圍擇用 |
| 實際瀏覽器互動、載入、錯誤與不同尺寸 | 可用的瀏覽器工具，以及需要重複執行時的 Playwright 測試 |
| 具體效能或網路瓶頸 | 當環境有對應能力時，使用 web-perf／DevTools 診斷 |

[Web Design Guidelines](https://github.com/vercel-labs/agent-skills/tree/main/skills/web-design-guidelines)可以提供程式審查依據，但不能單靠讀原始碼就宣布完整產品通過所有可及性要求。鍵盤、焦點、提示與操作狀態，仍要在真實介面確認。

例如 Impeccable 已完成同一範圍的技術 audit，就不預設再執行一輪相同的 Web Design Guidelines。若另一項檢查能補上不同風險，再說明範圍後使用。

驗證畫面時，我會挑與變更相關的狀態：長標題、空資料、載入中、送出失敗、權限不足、鍵盤操作或目標手機尺寸。不是每個專案都要照同一張表全部重跑，但承諾支援的核心情境不能漏掉。

## 三個常見任務，實際會走到哪裡？

### 情境一：從零做一個新的後台

沒有方向時，由 frontend-design 分流到 Product Design；先選視覺與資訊結構，保存核准來源，補齊重要狀態與 Gherkin，再使用既有元件實作。最後分別驗證畫面與行為。配色或圖表有疑問才查 UI/UX Pro Max。

### 情境二：手機上表單按鈕被遮住

直接進 Impeccable 的相關局部工作，查明容器、捲動與固定區域的關係，沿用原本設計。驗證實際手機尺寸與送出流程，不重做品牌方向。

### 情境三：產品已有固定品牌，要重新整理首頁

如果明確選用 Hallmark，就讓它負責這次 redesign 的方向。方向核准後交接實作，不再請 Product Design 提供另一批競爭方案。後續需要 Impeccable 時，限定在明確的精修問題。

## 開始前，先把主責與授權說清楚

這段提示詞可以當作工作起點：

```text
先判斷這是視覺探索、忠實還原、既有 UI 改善，還是技術審查。
有明確指定的技能或核准設計就直接沿用；每個階段只選一個主責。
缺少具體參考時再查 UI/UX Pro Max，不重複訪談或另建設計系統。
完成後回報實際畫面、行為驗證與尚待人工確認的部分。
這次只做本機設計／實作，不發布、部署或傳送給他人。
```

好的交接會帶走產品 brief、核准來源、tokens、相關驗收條件與仍有效的檢查結果。下一個階段從這些成果繼續，而不是為了換一個工具，把前面的工作重新做一次。
