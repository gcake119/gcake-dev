## Context
The handoff approves queue policy but prohibits production activation before acceptance. Git owns content and manifests; Admin runtime remains D1-owned.
## Goals / Non-Goals
Deliver gated orchestration and an installable Hermes poller. Do not change bodies, manifest order, Admin UI or configure production credentials.
## Decisions
### Git queue journal
Use a dedicated Git operational journal for this Actions-only queue, an explicit exception to the general D1 operational-state direction. Whole-branch non-force pushes reject CMS races. D1 was considered but its production configuration is not assumed. Initial readiness is reconstructed from first-parent Git commits in the current continuous eligible period, combined with complete-manifest readiness, then persisted. This preserves FIFO across multiple CMS saves within one polling interval. Missing history uses first durable observation; filesystem time is never used. Incomplete groups lose eligibility; content-only edits retain FIFO. New membership resets group readiness.
### Deployment recovery
Reserve and change publication metadata together before building. A pending attempt blocks new selection until RSS and the public page are verified. Failed builds retain the attempt for retry; published frontmatter is publication intent rather than confirmation. Use the existing pages concurrency group and latest main checkout; never force-push or merge on conflict. Check branch head before deployment. Existing push and hourly recovery stay in place. Only the latest due slot can be claimed; older missed slots are not backfilled.
### Hermes outbox
Install a standard-library Python poller under the Hermes account with a private SQLite journal and exclusive process lock. Canonical local URLs are identity, GUID is recorded as evidence. First successful feed initializes historical items silently. HTTP verifies local article HTML canonical. Claim before sending; ambiguous Telegram failure remains uncertain for manual reconciliation, never automatic resend. Dry-run uses a separate database.
## Implementation Contract
Boundary hardening: live construction/poll and production transport each check the activation flag. Test mode constructs its own validated mock sender from `mock_api` and rejects injected sender overrides. The shared HTTP transport validates fixed production endpoint/activation or fixed synthetic loopback endpoint/chat before opening an HTTP client. Non-live paths cannot resolve to the default live SQLite path, even before it exists. Existing state is checked read-only for mode/site before chmod or schema writes; status uses read-only SQLite and does not create missing files. Reject database/lock symlinks and hard-linked state files; resolved parent aliases still cannot bypass reserved-path or stored-scope checks. Trusted OS owners can edit Python/config/state, so this is accidental misuse and interface hardening, not a sandbox against that owner.

Controlled mock delivery is explicitly selected with `--test-delivery --site http://127.0.0.1:<port>/<base>/ --telegram-api http://127.0.0.1:<port>/ --db <private-test-path>`. Reject missing parameters, live/dry-run mixing, credentials in URLs, controls, query/fragment, non-loopback destinations and redirects. Use constant synthetic bot/chat credentials; never read private Telegram environment credentials in this mode. Exercise the same outbox claim/send/acknowledge behavior with mode `test-delivery`, not the production `live` flag. Bind state to mode and site; legacy unbound production state is compatible only with the fixed production site. Tests run actual CLI subprocesses and loopback HTTP servers, including lost replies, retry/backoff and restart. In scope: test transport, state isolation and mock integration. Out of scope: remote test hosts, real Telegram, Hermes installation, production deployment or activation. Arbitrary HTTPS host overrides were rejected because they broaden the production trust boundary.

Queue JSON version 1 stores membership fingerprints and readyAt, activation startedAt, active series, completed slots and one pending attempt; it does not copy manifest order or bodies. CLI ingest/reserve/confirm operations read complete manifests and validated frontmatter, preserve raw article bodies and YAML ordering, reject unsafe paths and inconsistent states. Writes require EDITORIAL_RELEASE_ENABLED=true, main branch and workflow/environment approval. Reservation is one article at latest Monday/Thursday 07:00 Taipei, eligible at that instant. Confirmation requires expected RSS URL and successful canonical HTML carrying the transformed Markdown SHA-256. CMS pending source changes and deleted active manifests require explicit operator repair. Missing/deleted pending articles block. Manual publications are excluded; an in-progress complete group resumes before waiting groups. Workflow recovery processes pending even on pushes, but new reservations only occur on scheduled/manual runs. Hermes hourly job backs off on outages, sends title/URL/Taipei date and never sends before page verification. Verify via test:editorial, test, check, build, Python unittest and a real local static-deployment rehearsal. Remote deployment and Telegram acceptance remain human gates.
## Risks / Trade-offs
- Git push permission requires protected environment acceptance and narrowly scoped token; defaults remain disabled.
- CMS can write after the pre-deploy head check; an old artifact may briefly deploy. Pending confirmation blocks further consumption and hourly latest-head builds recover. Strong atomic Git/deployment coordination would require CMS cooperation.
- At-most-once Telegram avoids duplicate sends but ambiguous failures can lose a notification; operator reconciles privately.
- Activation requires durable ingestion before 07:00. Git commit evidence preserves existing readiness but startedAt excludes pre-activation slots. Future manually scheduled chapters cannot count as already public.

### Unattended release preparation
In scope: a dedicated GitHub App token per prepare/confirm job, contents write scoped to this repository, readonly GITHUB_TOKEN, non-persisted checkout credentials, environment-only HTTP Git authentication, an authenticated remote allowlist, read-only GitHub configuration audit, and owner instructions. Out of scope: installing/granting App permissions, changing rulesets/environment reviewers, production writes, real Telegram or merging this PR. No credentials are added by this change.
Use official create-github-app-token v3 pinned to a full commit, client ID repository variable EDITORIAL_APP_CLIENT_ID and private key environment secret EDITORIAL_APP_PRIVATE_KEY. Generate after dependency installation and full pnpm test/check with production flags forced false; request contents write for only github.event.repository.name. Git push accepts only the fixed HTTPS remote, uses GIT_CONFIG environment for its one subprocess and hides raw push errors. No fallback to GITHUB_TOKEN. Existing skip-ci queue commits prevent App pushes from recursively triggering push-based deployment/validation; scheduled/manual recovery remains authoritative. This means push-triggered CI does not attest generated release commits; pre-release validation and pending/public confirmation still apply.
Owner-only unattended environment has no per-run reviewer and only Branch main, but is provisioned only after explicit permission acceptance. On 2026-10-12 the owner approved retaining direct CMS saves: the review ruleset grants Always bypass only to the dedicated editorial App and existing gcake-publishing-cms-2026 (App ID 5109954). Both bypass PR and status-check requirements; a separate integrity ruleset blocks force/deletion without any bypass. Ordinary code updates still require PR/CI. The CMS installation 165836027 selects only gcake-dev, with contents write and actions/metadata read, verified in owner UI; preview and production share this CMS identity. Real protected-main CMS writes remain unverified. Contents write cannot be restricted by file path at the provider, so App/private-key compromise can change other content: writer path allowlisting is an application guard, not a provider sandbox. Never reuse CMS credentials for editorial jobs or grant Workflows/Administration/Secrets write. Private App metadata may be unavailable to the owner gh session (HTTP 404); audit reports incomplete rather than changing visibility or minting a token to work around it.
Read-only audit uses gh owner login only to read environment, variable/secret names and ruleset metadata. It does not mint tokens, read private key values or prove installation scope. It reports configuration gaps and always leaves activationReady false with outstanding provider/human gates. Two keys on different scopes: public client ID repository variable; private key only editorial-release environment secret.
Stopping requires queue flag false, disabling Pages scheduled workflow/cancelling active runs while pending intent exists, plus Hermes live flag/job stopped preserving DB. Cached job flags and the pre-deploy head check are not an instantaneous stop or CMS transaction lock; no such claim is made.

### Read-only Actions Secret acceptance
Reuse the existing default-branch-registered deploy-pages workflow only as a dispatch entry point; add choice mode=secret-check plus expected_sha. All prepare/build/deploy/confirm jobs exclude secret-check. A no-secret preflight permits only manual dispatch on feat/editorial-release-queue, exact 40-character SHA and false/unset EDITORIAL_RELEASE_ENABLED/RELEASE_AUTOMATION_ENABLED. Only its successful dependent job references editorial-release; it has contents-read GITHUB_TOKEN, no checkout or dependency install, pinned official App action requesting contents read, fixed GitHub GET identity checks, and default token revocation. The private key retains its installed App's underlying write capability even though this token is read-only: allowing a feature branch exposes all environment secrets to workflows on that branch. Do not change that policy without the owner's separate explicit approval. Restore main-only immediately after completion/failure. This acceptance proves key/identity and read token creation, not delivery or production acceptance.

Installation repository responses do not guarantee user-style permission booleans. Enforce contents-read in the pinned action mint request, constrain repository names, verify installation/App and the sole repository, then perform a fixed content GET. Optional permission metadata is additional rejection evidence only, not token introspection. Never test by attempting a real write; successful read alone does not establish absent write capability. A consumed single-run grant must not be replayed after a code fix.
