## Context
The owner initially selected retention of the 4 GiB cap and planning only, then explicitly authorized implementation, archival and dependent timestamp adoption on 2026-10-26. Current authority usage is 4,823,534,781 bytes, including a 2,216,043,633-byte first-runtime backup. The timestamp candidate projects 5,197,180,069 bytes. The active 4fe release and ready/live gate are intact. Public metadata was inventoried; the old f36 proposal passed verification, but reading a 40a dependency file required root. Full payload and protected operational-reference verification therefore remain execution preconditions, not completed acceptance.

## Goals / Non-Goals
In scope: a narrowly allowlisted, reversible cold-archive operation and restoration plan, preserved metadata and audit identities, execution-time reference checks and unchanged capacity arithmetic.
Out of scope for the archiver: increasing limits, deleting or compressing recovery data, moving first-runtime, changing installed controls, adopting the timestamp runtime, restarting Gateway, changing cron or notification history, automatic retention policies, cloud upload and new dependencies.

## Decisions
### Exact retirement eligibility
Use only the three identities listed in archive-plan.md. Keep active 4fe, initial managed 8e, successful notification release f36, new fcb proposal and all private backups. Check operational references under existing updater exclusion and maintenance locking, including active/gate, next-candidate, recovery journal, live leases and runnable entry dependencies. An earlier audit receipt mentioning a package is not an active reference; preserve that receipt and record the package's archive location. Any operational dependency or unverifiable evidence rejects the entire planned set before relocation; do not automatically substitute older versions.

### Reversible same-filesystem cold archive
Proposed destination is /usr/local/share/gcake-hermes-archives/20261026-retired-versions, outside the hot managed authority but on the same device, root-owned mode 0700 and without runner-write ACLs. Its bytes remain reported as retained system storage, never claimed as disk reclaimed. Move full directories by atomic rename after all preflight checks, preserving bytes, relative links, owner/mode/ACL/xattrs. Preserve authority manifests and approvals at original locations. Use a hash-bound inventory and progress receipt stored in the archive; persist intent before each rename and progress afterwards. Verify complete payload and metadata after each move. No archive program is executed. A same-device prerequisite avoids introducing copy/delete or compression handling.

### Capacity and notification boundaries
Keep the existing updater unchanged. Fresh full authority usage plus candidate size must fit its exact original threshold. Archival alone sends nothing and changes no runtime state. Later runtime adoption remains in clarify-original-site-publication-times. Restoration returns exact directories without selecting an archived runtime. A return to the already over-budget baseline is reported explicitly and does not authorize another update.

## Implementation Contract
One foreground administrator entry supports plan, archive, resume and restore over the exact inventory; execution requires owner approval of this proposal. Plan is read-only. Archive requires a hash-pinned allowlist and verifies all eligibility before any move. Reuse updater_guard manifest/tree checks and existing lock/lease/control APIs; never weaken their checks. Reject destination symlinks, unsafe ownership, cross-device moves and missing or divergent identities. Resumption compares recorded source/destination identity; a foreign destination is never overwritten. On ordinary failure attempt reverse relocation of completed exact moves, preserving the receipt even when recovery remains necessary. SIGKILL recovery uses recorded intent and actual identities, not guesses.
Public JSON reports status, phase, package identities, archive/original locations, measured authority/archive/candidate/projected bytes, limit_bytes, restore command and zero external effects; no secrets or private message contents. Statuses distinguish planned, archived, restored, blocked and recovery-required. Execution with a protected evidence gap is blocked. Check same-UID synthetic acceptance before implementation; validate positive eligibility, blocked references/tamper, interruption/foreign destination and exact 4 GiB/plus-one boundaries. Do not duplicate full Gateway or SDK qualification for a read-only/move-only tool.
Concrete risk is loss of a recovery payload or an operational reference. Existing updater verifies releases but has no archival transaction coverage. Extend the existing Python fixture/test patterns with small isolated filesystem cases and a scoped native metadata round-trip; no CI job, dependency or multi-runtime bundle is added. Development/PR tests run in seconds with tiny fixtures; root production execution supplies distinct ownership/reference evidence. Static filename tests alone are insufficient.

## Risks / Trade-offs
[Retired package still referenced] → foreground root checks live and recovery references; block the entire set on dependency or uncertainty.
[Interrupted move] → same-device rename, durable inventory and identity-based resume/restore; report unresolved recovery.
[Archive metadata changes] → restrictive destination, pre/post content and metadata verification; restore at exact original location before any runtime use.
[Limited headroom] → measured projected headroom is only 208,205,950 bytes, approximately 198.6 MiB; this resolves this update estimate, not unlimited future growth. Report capacity without an automatic archiver.
[No off-device backup] → archive remains on the same disk and does not protect against disk failure; originals are retained for local recovery only.

## Migration Plan
After the owner’s explicit execution authorization, implement test-first, run the complete affected Hermes gate, prepare a hash-pinned administrator package, then perform root preflight and archive with before/after receipts. Verify active ready/live identity, service health and unchanged job/ledger fingerprints without sending a notification. Resume the existing timestamp adoption only after archive verification and a fresh capacity calculation, using its original managed qualification. To undo archival, use exact inventory restoration and verify content/metadata; block on occupied original paths and report any restored over-budget state. Never run a broad prune or weaken the updater.
