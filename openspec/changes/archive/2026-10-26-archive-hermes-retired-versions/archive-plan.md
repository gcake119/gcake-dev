## 封存與還原方式

建議封存目的地：/usr/local/share/gcake-hermes-archives/20261026-retired-versions。由 root 擁有，權限 0700，確認沒有讓 Hermes 或其他使用者寫入的 ACL。來源與目的地必須在同一個檔案系統，保留原本 proposal／release 分類與完整 digest。

先以既有維護鎖與 updater 排他鎖防止同時更新，核對 active、gate、next-candidate、復原 journal、現有租約及可執行入口的依賴。歷史回執保留並補封存位置；只出現在歷史稽核紀錄不直接視為仍被執行，但復原流程實際依賴原位置時必須停止。

全部前置核對通過後，記錄精確來源、目的地、manifest 身分、內容雜湊與 owner／mode／ACL／延伸屬性，再使用同磁碟的目錄 rename 搬移。rename 保留檔案內容、相對 symlink 及原有 metadata；每項完成後重新核對。每次搬移前後保存進度，確保中斷後能依真實位置與身分繼續或還原。

失敗時只將已搬移且身分吻合的項目反向 rename 回原位置，不覆寫其他內容。來源或目的地出現不同身分時停止並報 recovery-required，保留紀錄；禁止猜測、刪除或另選替代版本。不得從封存位置執行舊 runtime。

日後還原也必須明確授權，依同一清單搬回精確原位、核對完整內容與 metadata；不會自動切換 active。若還原後回到原本超過容量上限的狀態，明確報告後續更新仍會被原有容量檢查阻擋，不因此放寬上限。

## 驗證與執行邊界

本次已完成公開 active／ready gate、版本大小與 manifest 身分盤點。舊 proposal f36 可讀內容已通過既有驗證；舊 release 40a 的依賴檔案讀取遭系統權限拒絕，因此三份完整 payload 的管理員驗證與受保護使用關係仍未完成，不能宣稱已可安全搬移。

實作時先用小型隔離檔案情境測試正常搬移／還原、仍被使用、竄改、權限不足、中斷、目的地衝突，以及 4 GiB 正好／超過一 byte 的邊界。重用既有 Python 測試與檔案驗證工具，不新增 CI 工作或依賴，也不複製整套 Gateway 測試環境。最後的 root 操作另保存封存前後的完整核對、現用版本、服務健康與原工作／帳本未改動證據；不發測試 Telegram。

本次規劃不調整已核准候選的 next-candidate 指標。執行時必須確認它仍精確指向本次 fcb 候選且沒有其他更新工作，才可封存。封存驗證完成後，原站時間修正仍須回到既有受控更新流程，等待自然 dry-run 並完成 live 讀回；封存完成不等於時間修正已上線。
