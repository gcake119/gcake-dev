## 本機 RED 與修正

沿用已核准 Freshness and source lifecycle boundaries 的 Budgets end during a large inventory 情境，以及既有 round／SQLite 驗收，新增慢來源、慢 main 查核、慢媒體三種情境。原實作在 120ms 的整輪預算後仍持續等待，在 800ms 看門時間仍未結束；fixture 使用 1500ms 的慢讀並保留原 ID／intent，沒有真實網路或 provider。首次 media fixture 缺少第三個 fetch 參數，得到的是 READ_INCONCLUSIVE，屬無效期限重現；改為使用 fallback fake fetch 後，也取得真正 still-running RED。分別保存原始 logs，沒有把無效重現當作通過。

根因是只在進入迴圈與 authority() 檢查 deadline；媒體與同步 git ls-remote 都有自己的 30 秒期限，且同步 child process 會擋住 event loop。改為每次完整 source check 共用剩餘 deadline：

- 對完整來源／媒體／遠端查核使用有界 race；到期回 SUBSTACK_DRAFT_BUDGET_EXHAUSTED，不繼續 dispatch 或宣稱 observed。
- 傳給來源 builder 的 fetch 同時保留既有請求 signal 與整輪 abort，取消尚未完成的媒體讀取。
- git ls-remote 改為非同步 execFile，timeout 取剩餘預算與原 30 秒上限的較小值，並接受相同 abort signal／SIGKILL；不再以同步遠端程序阻塞整輪 deadline。
- 來源晚回來時仍先核對 abort，不能再啟動 main 查核；保留 incomplete coverage 與原 intent，沒有 fallback 到 provider 寫入。

三項新驗收 GREEN，局部草稿＋API 共 56／56 通過；測到媒體取消、來源晚完成後不查 main、零 provider dispatch、原 intent 不變。沒有修改產品預算上限、Gherkin 或新增依賴／CI／測試層。
