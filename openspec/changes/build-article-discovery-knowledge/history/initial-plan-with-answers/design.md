## Goals / Non-Goals

**In scope:** automatically refreshed public article knowledge; factual link relationships; automatic related/further reading; improved keyword search; separately activated semantic search and cited questions; release, budget, privacy, and verification contracts.

**Out of scope:** changing authored Markdown to insert generated links; changing topic taxonomy automatically; ingesting drafts or private repositories; browsing arbitrary external URLs; a reader account or chat-history service; retraining a language model; Admin redesign; source slug/canonical/publication policy changes; Substack, newsletters, notifications; autonomous scheduling; new required CI workflows or changes to branch protection. Saving a draft is not publication, and an article's scheduled time alone is not proof of a deployed site update.

## Decisions

### One public corpus with automatic release updates

Use loadReadingCatalog as the eligibility entrance, then hydrate body, topics, source identity and headings for each selected article. Build from the same source tree, frozen publication instant, imported snapshot and configuration as the site. Source eligibility is rechecked against local public-date rules and imported published membership. Preview builds never upload or activate their corpus.

Each article has articleId=source namespace plus source-local identity, sourceRevision=content digest, local readingHref, canonicalUrl, title, description, topics, series, dates, extracted body, headings, terms and outgoing authored links. Slugs alone are not globally unique. Preserve an upstream stable ID where one exists. A rename with no stable ID and no explicit migration mapping is removal plus addition; never invent redirects or silently combine articles by title.

Passages carry articleId, revision, passageId, heading path, verified anchor and plain text. Passage extraction reuses the rendered Markdown/MDX pipeline and existing heading identities; it does not execute interactive MDX to obtain text, retain script/style/hidden content, or use regular-expression-only markup removal. Keep code as a distinct low-weight searchable field for exact technical queries, not vocabulary noise. Start with heading/paragraph groups bounded by 800 Unicode code points and one preceding paragraph of overlap, capped at 120 code points; enforce the chosen embedding model's actual token limit before upload, splitting further without dropping source provenance. Article-level retrieval deduplicates overlapping passages.

corpusId hashes sorted eligible article revisions, external snapshot identity, extraction/normalization/alias/ranking versions and schema version; generatedAt is informational and excluded from content hashing. Unchanged article extraction and embeddings reuse content-addressed cache only when the entire relevant tuple matches. Build one current-release graph and lexical index to incorporate inverse frequency, backlinks and cross-article changes. Do not claim ranking is unaffected when only one article changed.

Trigger refresh in the existing build path on every actual publication, edit, rename, deletion or withdrawal release. No periodic watcher is required. A future date becomes eligible only through a real subsequent build/release; document that static sites cannot become fresh merely as time passes. Automatic here means no separate per-article indexing action after the established publication workflow runs.

### Automatic terminology and explainable article connections

Normalize NFKC and case into search keys while preserving original display text and technical punctuation. Use pinned Node Intl.Segmenter zh-TW word segmentation plus Han bigrams for recall; serialize tokens so the browser does not retokenize indexed articles differently. Query normalization uses the same implementation, with deterministic bigram fallback when Segmenter is unavailable. Treat C++, C#, .NET and version strings as protected technical tokens. Use a versioned stop list and term-frequency/inverse-document-frequency ranking. Capture up to 20 supported terms per article and evidence passages. Labels and rare technical identifiers receive controlled boosts rather than automatically becoming official topics.

Extract only explicit synonym/acronym patterns as equivalences, including a full term followed by an acronym or bilingual definition. Ambiguous patterns become non-expanding candidates. A small optional alias configuration supplies tested corrections; routine articles require no manual keyword work. Every accepted alias records its origin and evidence or operator correction. Do not merge Simplified and Traditional Chinese through arbitrary character substitution; add tested, explicit equivalences when evidence supports them. No mandatory automatic translation or spell correction.

Parse authored anchors and normalize known local/base-path, upstream source and canonical URL aliases; strip fragments for article identity, preserve anchors for passage navigation, deduplicate incoming/outgoing edges and reject unsafe schemes. Classify known hidden local targets as non-public without revealing metadata. Do not visit external links; external references display only safe authored titles/URLs, and receive no invented local backlinks. A generated recommendation is never an authored citation.

Related ranking uses current-corpus lexical similarity, topic overlap and, after Stage B activation, optional article-vector similarity. Start deterministic: 0.7 normalized lexical cosine + 0.3 topic Jaccard; require at least two shared non-stop terms and score >=0.15, with articleId as the stable tie break. Pin this version before acceptance; any change to thresholds changes the ranking tuple and reruns affected quality evaluation.

Further reading uses a different coverage objective: candidate score is 0.6 shared-topic relevance + 0.4 supported new-term coverage, with relevance >=0.15 and at least two supported terms absent from the current article. Choose greedily to add coverage rather than duplicate the selected candidates. A reason such as '延伸了解：失敗重試、排程' is a deterministic rendering of supported candidate terms. Do not assert that similarity proves prerequisites, progression, author endorsement, or factual citation. If no candidate qualifies, omit the group. AI-generated reasons are unnecessary for the initial release.

Each recommendation group has at most three articles; allocate further reading first, then related, deduplicating across those two groups. Keep factual citations available even if the same target is recommended. Similarity enrichment is optional; model failure regenerates connections from current deterministic evidence, never an old graph.

### Ranked search and restrained reading layout

Preserve the single header GET search form and its query value. The results page adds labelled topic and series filters, a relevance/default or newest sort choice, count, ten results per page, clear filters, retry and working topic/series navigation. URL keys are q, topic, series, mode, sort and page; unknown values normalize visibly to defaults, out-of-range pages clamp after counting. Filters reset page to one. Use lexical as default; semantic is a separate explicit mode, not triggered by typing.

Use an inverted text index and BM25 field ranking: title=5, headings=3, supported terms=2, description=2, body=1, code=0.5; BM25 k1=1.2 and b=0.75. Apply an exact-title tier then exact phrase boost; merge alias expansions with lower weight than original terms. Within matching evidence, full token coverage ranks above partial coverage. If no full-coverage results exist, label partial matches as such rather than silently pretending every term matched. Shared fixtures establish Chinese and technical-token behavior. Sorting ties use publication date then articleId. These are initial testable choices, not measured quality claims.

Return title, context, topic labels, a query-specific excerpt of roughly 120 display code points and a section link when verified. Mark matches with text nodes and mark elements, never HTML interpolation. The displayed count refers to unique filtered articles. Local top-five suggestions come from current corpus terms, are labelled suggestion links/buttons outside the text input rather than a custom combobox, and create no remote typing requests. No-result suggestions never silently replace the query. Malformed URI parameters recover visibly; blank input has no results/provider calls; query maximum is 200 code points; filters apply before pagination and count.

Article layout: preserve header/TOC/body; append further reading, existing compact subscription, previous/next series navigation, related reading, then a native disclosure with authored outgoing/incoming references. Links use full titles and restrained editorial rows with separators, not a card grid. Empty groups disappear. Reuse 44rem reading width, 62rem shell, existing blue tokens, light/dark themes and 700px breakpoint. Do not add another page input, sticky recommendation rail, hover-only previews or a nonfunctional question UI. No-js reading connections stay useful; search offers topic/series fallback. Keep focus order, status announcements and 44px control targets.

### Separate semantic service with current-release enforcement

Stage A runs fully on the static site. Stage B adds apps/search-worker as a separate public Worker, avoiding Admin cookies, GitHub write credentials and publication routes. It owns real behavior: admission, public-release validation, query embeddings, Vectorize retrieval and ranking. Its deletion removes semantic search and answers but leaves static search and article panels working. One provider adapter maps embeddings and generation; no chain of forwarding wrappers.

Recommended deployment shape is Cloudflare Workers + Workers AI + Vectorize, with a small D1 database only for durable admission budgets and activation configuration. Public passage JSON remains content-addressed static site output; do not add R2 for the same data. bge-m3 is the initial multilingual embedding candidate, not a measured winner; record actual returned dimension and model/configuration digest and use the identical embedding configuration for passages and queries. A pinned Chinese-capable Workers AI generation model is selected by the Stage C evaluation gate, rather than guessing from model marketing. Do not create resources or call models during planning.

Before each remote request, the Worker fetches the site's fixed, allowlisted discovery-manifest URL with cache bypass and a two-second timeout, validates its expected deployment origin and schema, and requires requested corpusId to equal deployed corpusId and configured active semantic corpusId. It never fetches a caller-supplied URL. Vectorize namespace is the release corpusId; query filters include topic/series as applicable, and returned IDs/revisions are joined and checked against the exact allowlist. Provider metadata is not proof of current visibility. Recheck active manifest after generation before returning an answer; a changed manifest discards that answer. Missing, conflicting or stale manifests disable remote paths, while static fallback remains available.

Publication sequence: build static assets and optional embeddings for a staged corpus; stage passage vectors and verify read-after-write readiness; deploy site through the existing authorized path; read back the deployed manifest and representative article URLs; promote semantic activation only to that confirmed corpusId. During the gap lexical is available and semantic reports unavailability. Remote staging is never automatic authority to deploy the site. Modified Pages delivery integration is a separately reviewed implementation change to existing orchestration, preserving stale-head and release checks. No new scheduler or mandatory workflow.

Once the release updater and nonzero budgets have been explicitly activated, subsequent eligible site releases automatically prepare changed embeddings and promote a matching semantic corpus within that standing authorization; no per-article selection, reindex button or repeated per-article activation approval is part of the product flow. Failed enrichment leaves the new site's lexical mode available and records an operator diagnostic; the next authorized release/update attempt can retry the failed content-addressed units. It never silently creates a new background scheduler.

Withdrawals/deletions activate the new site corpus even when new vectors are unavailable: this deliberately makes semantic unavailable rather than retaining deleted knowledge. Old namespace cleanup happens after activation and request expiry. Never route callers to old corpus IDs. Existing downloaded static pages cannot be remotely erased; current-release requests exclude removed articles, while cached old site copies follow normal browser/cache limitations. No claim of instantaneous global revocation across third-party caches.

### Grounded answers with bounded remote execution

Stage C adds an explicit '依文章內容回答' action, separate from search. Place the remote-processing notice before first semantic/question submission, with keyword search always available. Question uses the existing q value and current filters; no conversational history or extra input. One request retrieves at most 12 passages, deduplicates and supplies at most six passages from three articles within a 6000-token total context budget, reducing to the chosen model limit. Use structured answer claims with passage IDs, source quotations and clear uncertainty. Insufficient retrieval evidence yields abstention before generation.

The model sees content as delimited data and has no tools, browsing, filesystem, credentials, or ability to change retrieval scope. Validate output size/schema and that every cited ID belongs to the current retrieval set with an exact supporting source quote; produce links from trusted corpus data, not model URLs. Mechanical citation/quote validation does not prove entailment: the Stage C human-rated sample separately checks that every factual claim is supported and uncertainty preserved. A failed sample blocks public activation. At runtime invalid structure/citation/quote yields a safe unavailable result plus verified articles; do not stream unvalidated factual prose. Unsupported questions return '文章庫目前沒有足夠資料回答'.

Defaults: semantic and answers disabled, remote daily budget=0. Before activation, record explicit nonzero daily request/token/currency ceilings, model IDs, limits, privacy terms and authorization. Missing prices or quota configuration fail closed. D1 atomic conditional reservations enforce shared daily call and maximum-token allowance before provider calls; reserve worst-case token/currency cost using verified current rates, then settle actual usage when known, retaining reservation on unknown outcome. Never treat a per-isolate counter, CORS or an approximate platform rate limit as a global spending cap. Provider/service charges outside model execution require separate monitoring; do not promise the reservation controls the entire cloud bill.

Public endpoints enforce <=4KiB JSON, 200-code-point query, ten results, 5-second semantic deadline, 15-second question deadline, <=800 output tokens and no automatic generation retry. Per-client throttling starts at 10 remote requests/minute using a short-lived keyed hash at the admission boundary, not raw IP storage; remove window keys after 10 minutes. Daily aggregate usage records expire after 30 days. Reject excess requests with 429. Restrict CORS to exact site origins, but treat unauthenticated endpoints as publicly callable and rely on real shared admission. No logs of raw questions, queries, passage bodies, IPs or generated answers in application telemetry. Audit platform access logs, provider retention and legal/privacy copy before activation; document residual third-party processing instead of promising zero retention.

## Implementation Contract

Static output: discovery-manifest.json contains schemaVersion, corpusId, sourceTree, frozen eligibility instant, snapshotDigest, configurationDigest and asset digests. Content-addressed article metadata, term/alias, inverted-index, passage and connection assets share that identity. Preserve the existing search-index route as a compatible entry point during migration; use a schema-discriminated payload and client that can handle the previous array for one release. Old clients must not receive an incompatible object at the old URL: retain the old array there, and expose the new manifest/index at separate versioned paths until old clients age out.

Builder interface: buildPublicDiscovery accepts the eligible catalog, hydrated public sources and frozen release configuration and returns validated assets plus diagnostics. Stage A uses no provider. It checks unique identities, safe URLs, valid target links, passage provenance, alias evidence and visibility. Cache schema mismatch discards derived cache and regenerates. Invalid public metadata/source fails the candidate build; optional semantic work is a separate step and cannot fail the baseline static build. Expose local inspection and evaluation commands through package scripts when implemented; add no commands during planning.

Worker interface: POST /v1/search accepts {q, corpusId, topic?, series?, page>=1, sort:'relevance'|'newest', limit<=10}; returns {corpusId, mode:'hybrid', total, page, hasMore, candidateLimited, results:[{articleId, title, readingHref, excerpt, passageId}]}. Worker obtains lexical and passage assets from the fixed deployed manifest, applies filters, and fuses lexical and semantic article ranks with reciprocal rank fusion k=60; browser does not send arbitrary candidate IDs or URLs. Build a deterministic pool of up to 50 unique articles from lexical and vector candidates, apply requested sorting, count that pool, then paginate. total describes the ranked candidate pool, not an assertion that every semantically relevant article in the library was examined; candidateLimited discloses a reached candidate ceiling. Query/result caching includes the full query/filter/model/corpus tuple and lasts at most five minutes; page changes do not reshuffle a cached pool. POST /v1/answer accepts {q, corpusId, topic?, series?}; returns {status:'answered'|'insufficient-evidence', corpusId, claims:[{text, citations:[{articleId, passageId, quote}]}], sources}. Errors are {code, retryable, fallback:'keyword'} with 400 INVALID_QUERY, 409 CORPUS_MISMATCH, 429 QUOTA_EXCEEDED and 503 SERVICE_UNAVAILABLE/ANSWER_UNVERIFIED. Origins/configuration remain operator settings, never query parameters. Reject unknown JSON fields and remote filters not present in the active corpus.

Use abort plus a monotonically increasing request token in the browser; ignore stale responses across queries, filters, mode and navigation. Remote timeout/429/409/503 retains current lexical results and shows a concise explanation, not a fake empty result. No raw responses rendered as HTML. Preserve JavaScript-disabled article connections and functional navigation.

Concrete examples in specs are contracts, not production article claims: A cites B twice yields one edge; C++ stays distinct from C#; same slug from two sources yields two identities; a new deployed article appears without a separate index action; edited/deleted passages disappear in the new release; unavailable semantic service never prevents keyword search.

## Verification and complexity budget

Reuse Node's existing test runner for corpus, token/rank, relationship, manifest, budget and citation contracts, integrated into existing public/workspace aggregates. The concrete coverage gap is cross-article visibility/revision correctness and new retrieval/ranking behavior. Acceptance starts as failing observable examples from all four specs before implementation; unit tests fill only logic gaps. Do not test source strings as proof of retrieval, and do not multiply the same cases across every layer.

Use one existing Playwright installation and a bounded new browser suite only for header GET state, filtered/deep-link/back navigation, retry/race/fallback, safe highlighting, keyboard status, both themes and 390/320px layouts. The purpose is DOM interaction and real layout, which Node contracts cannot prove. Run this suite locally for affected UI; do not add a parallel mandatory CI job or heavyweight browser dependency. Retain screenshots and run metadata. Synthetic fixtures go in isolated temporary/build output and are removed through the same verification script on success/failure/interruption. No Docker is needed.

Quality evaluation is a bounded release exercise, not a model-call job in every PR: prepare 40 source-grounded queries with graded expected articles (10 exact/technical, 10 Chinese multiword, 10 explicit alias, 10 paraphrase), plus 10 no-answer prompts and 5 hostile/malformed evidence cases. Split query IDs 20 tuning/20 held out, balanced across categories, and record assessors, source corpus and relevance judgments before tuning. Target held-out Recall@5 >=0.85; hybrid >=0.90, improve or equal lexical nDCG@5 and no exact-title rank regression; all no-answer/hostile cases must abstain or fail safely. At least 20 recommendation panels receive relevance review; target >=0.8 relevant items per nonempty group and 100% evidence-valid reasons. An empty group is valid when the source offers no suitable candidate. These are proposed acceptance thresholds, not measured results.

Stage C evaluates 20 supported questions, the same 10 no-answer prompts and 5 hostile cases; 100% displayed citations resolve and support their claims under review, and 100% unsupported/hostile cases abstain or fail safely. Report every failure, raw sample counts and quality limits. Automated quote validity is reported separately from semantic/human ratings.

Performance targets are provisional release gates: <=500KiB compressed initial keyword assets; corpus passage text loaded only when required; on a recorded mobile-equivalent profile use five cold loads and twenty warmed queries, report payload, device, throttling, medians/p95 and max rather than inferred savings. Target warm lexical p95 <=200ms and semantic p95 <=3s on the sampled environment; remote deadlines still govern failures. If payload/latency fails, first separate compact metadata/postings from body assets and cache by corpusId. No unmeasured scalability claim or cost-savings claim.

Required pre-push local commands remain the existing affected project complete gate derived from validate-pr: pnpm test, pnpm check, pnpm build:all, pnpm release:dry-run, pnpm editorial:rehearse; do not separately rerun commands already inside aggregates. Planning runs only Spectra validation/analysis and file-scope checks, not application tests or model evaluation. Cloudflare feasibility read-only documentation lookup does not prove provisioned bindings, provider availability or application quality.

## Risks / Trade-offs

- Wrong links or cross-source identity collision -> namespace identities, verify anchors and canonical aliases, never infer citations from similarity.
- Automatic aliases drift -> evidence-required extraction, bounded expansion, versioned regression examples and inspectable corrections.
- New public API consumes quota -> separate Worker, durable atomic admission, zero budgets by default and explicit activation; extra D1/Worker maintenance is justified only for remote modes, not Stage A.
- New semantic service duplicates lexical responsibilities -> shared discovery contracts and fixed static assets; one provider adapter, one browser lexical fallback, no independent content database.
- Generated answers cite real but irrelevant text -> separate support evaluation, no unvalidated streaming, failure/abstention and independent activation.
- Static and provider releases cannot switch atomically -> stage, verify deployment, activate matching corpus, return keyword fallback during mismatch.
- Ranking quality has no existing human baseline -> fix the judged sample before tuning; failed held-out evaluation blocks that milestone instead of reducing thresholds silently.
- Build and provider latency -> content-addressed reuse, optional enrichment, no model dependency in baseline site publishing.

## Migration Plan

A: add versioned static assets alongside the old search index, switch new client, add automatic connections and run deterministic/browser/quality gates. Amend current design documents with the adopted changes. Public deployment is a separate authorized step.

B: after A is stable, provision an isolated semantic staging service only when authorized, run the fixed real-provider evaluation, record dimensions/prices/privacy/budgets, stage a matching corpus and explicitly activate semantic mode. No activation from synthetic pass alone.

C: after B meets retrieval quality, evaluate the pinned generation candidate and citation support, then explicitly activate question mode independently. Maintain static mode at every step.

Rollback: disable answers first, semantic second; serve current-release lexical assets and deterministic panels. Roll code forward with current content visibility when removal occurred; restoring an old artifact that re-exposes withdrawn articles is forbidden. Retire old namespaces and previous index clients only after deployment and in-flight request expiry are verified.

This is one product plan with three delivery milestones, not one release. Before implementation, split a milestone further if its reviewed implementation units exceed one hour or independent release ownership; keep these accepted scenarios and dependencies unchanged rather than broadening a single PR. No commitment to engineering duration is made from the document count.

## Activation decisions and evidence to resolve during implementation

No missing product decision blocks Stage A. Stage B activation requires a real multilingual retrieval comparison and observed model dimensions, not assumed quality or limits. Stage C activation requires a pinned generation model and human support evaluation. Exact hosting account, endpoint, resource bindings, nonzero budgets, current provider rates/terms and rollout authority are recorded only when that foreground activation is requested; absent values mean disabled, not implicit consent. These are explicit execution gates with fail-closed behavior rather than unspecified implementation work.
