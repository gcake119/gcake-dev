## Context
The owner already has a fixed read-only index endpoint, safe shared status/source readers, an Admin Worker with CMS_DB and a local heartbeat. Telegram publication notifications use a separate local Hermes runtime; its credentials are not browser data and are not assumed present in Cloudflare. The new execution instruction authorizes this scoped feature implementation. Production credential placement, additive migration and new schedule require a concrete reviewed release candidate and verified owner destination before activation.
Decision context: level2; ADR-001, add-readonly-index-status and the existing notification authority boundary apply. Existing index Cron, requests500/vectorQueries500, paidOverage0, original capacity and billing dates remain fixed. This adds a monitor scheduling/storage decision, documented here and in the ledger; no search policy change.
## Goals / Non-Goals
In scope: existing Admin Worker scheduled observation, isolated CMS checkpoint and event history, owner-only GET and a compact history section. Out of scope: modifying the search Worker, index schedule, old monitor bundle, quotas, source publication, model calls, full provider audit, browser push, email, unread controls, automatic renewal and new services/dependencies/CI workflows.
## Decisions
### Reuse Admin Worker and CMS storage
Add two additive CMS tables, index_alert_state and index_alert_events, in migration0008. This avoids a new Worker, queue, or local daemon. A sixty-second compare-and-set lease prevents overlap. The checkpoint and paused state are persisted separately from search data; it is never bound to search D1. A failed monitor cannot prevent fetch routes from serving. Cost: one existing scheduled handler, a small state write per round, bounded receipt reads and at most one Telegram attempt per incident; cold isolates revalidate three public immutable assets through the existing reader. Do not persist large public asset bodies in CMS rows or claim official cost savings. Simpler page-only refresh misses off-page failures; a separate Worker adds deployment and credentials without providing full-cloud outage detection.
### Bounded fixed-origin reads and qualified seed
INDEX_ALERTS_ENABLED defaults false in every environment; no default Cron is installed by source config. A production release explicitly installs fifteen-minute Admin Cron only after verification. INDEX_ALERTS_SEED is a bounded validated JSON object containing afterReceipt, workerVersionId and acceptedCorpusId; derive it from the contiguous accepted heartbeat receipt chain at cutover, not from a guessed cursor. INDEX_ALERTS_VALID_UNTIL is no later than original capacity evidence, INDEX_STATUS_VALID_UNTIL matches the actual independent token expiry. The existing immutable heartbeat bundle and its reviewed sources stay unchanged. The cloud observer uses INDEX_STATUS_TOKEN and existing parseIndexSnapshot, indexAssessment and createIndexSourceReader. Per-round deadline30s, per status5s, at most11x50 receipts, no retries or arbitrary redirects. Advance only a complete validated page after source validation; classify only at high-water. Version/gap/reset/read failure preserves the last verified page and pauses. The baseline accepted corpus stays quiet, including timing jitter in recent no-change intervals; new corpus completion is a candidate only.
### Journal before Telegram and stop uncertain outcomes
INDEX_ALERTS_TELEGRAM_TOKEN and INDEX_ALERTS_TELEGRAM_CHAT_ID are optional dedicated server secrets, with expected INDEX_ALERTS_TELEGRAM_BOT_ID validated against the token prefix. Inspect existing non-secret delivery identity/provenance before proposing reuse; do not print or commit token/chat values, copy local credentials without reviewed authority, or use a different destination. The release-only INDEX_ALERTS_ACTIVATION_CHECK flag is absent/false by default. When explicitly enabled for qualified rollout, a fresh accepted-baseline completion candidate may produce one clearly labelled activation_check notice, with the same durable deduplication and unknown-send protection; this verifies delivery without falsifying a new corpus or modifying index state. Ordinary accepted-baseline checks remain quiet. Use only fixed https://api.telegram.org/bot<TOKEN>/sendMessage with POST JSON, redirect manual and five-second signal within the round. Set no paid-broadcast options. Bound response bytes. Accept only HTTP success plus ok=true, safe message_id and matching returned chat.id. Persist sending intent before calling. Unique incident key hashes pinned runtime, corpus and reason; duplicate events are never resent. Explicit structured rejection becomes rejected; timeout, network failure, mismatched chat or malformed acknowledgement becomes unknown; both pause. If CMS acknowledgement fails after Telegram response, leave durable sending intent and recover it as unknown without resend. Never promise exactly-once delivery or owner reading.
### Conservative actionable events and deadline stops
At each invocation validate credentials, seed and configured expiries before external requests. Disabled or malformed config performs no external request and does not claim healthy. An existing paused state does not observe again. An expired config records an expiry event using last safe state, attempts at most one qualified notification and pauses. During observation require source/target/active consistency and continuity; source_changed and valid waiting stay quiet. indexAssessment stale, explicit blocked/ineligible/disabled/unknown_inference and unavailable pause with a safe reason. Capacity/billing eligibility from the safe snapshot is also enforced even for an accepted completed corpus. No automatic provider calls, search queries or renewal. Notification infrastructure running on the same cloud cannot independently prove a total Cloudflare outage; retain explicit limitation.
### Read-only owner history in the existing index area
GET /api/v1/discovery/index-alerts follows the current index-status session/owner checks, accepts GET without query/body and returns no-store. Missing migration returns safe503, not initialization through GET. Return schemaVersion1, monitor enabled/active/paused/not_configured, checkedAt, reason, validUntil, and up to20 events ordered by creation and key. Events expose id, corpusId, reason, createdAt, delivery, deliveredAt and safe numeric Telegram message id only when acknowledged; never chat id, token, raw errors or response bodies. Browser UI requests on mount and manual refresh only, twenty-seven-second bound, ten-second cooldown, cancellation on unmount, clear protected data on401/403, preserve timestamped stale history on transient failure. No added automatic polling loop: existing index panel retains its existing five-minute updates. Place a history subsection under progress. Use heading20px, body17px, metadata14px, spacing8/12/16/24px, existing secondary controls44px and semantic themes. Show records with content readable on320px, no retry or subscription controls.
## Implementation Contract
New runCloudIndexAlerts(env, fetcher, now) is called only by the Admin scheduled handler. A store port supports seed, lease, qualified checkpoint, pause, pre-send unique intent, final acknowledgement, uncertain recovery and bounded history. D1 store implements these on the two dedicated tables with atomic conditional updates. Pure incident classification and history parsing remain typed. Existing owner reader and local monitor sources do not change. Existing fetch runtime wiring supplies a history read closure only; history cannot cause sends. Tests first reproduce observable accepted-baseline silence, new completion, overlap, history gaps, expiry zero-fetch, unknown-send no-replay, unauthorized zero-access, and safe history states in existing Node/SQLite/Vue seams. No parallel agent or new test infrastructure.
## Risks / Trade-offs
Durable CMS state adds a migration and lease/journal maintenance. Network send and CMS commit cannot form one transaction, so unknown delivery stops rather than retries. A failed CMS may make cloud alerting unavailable; owner history exposes failure rather than claiming sent. Pin changes need intentional reseeding after review; old unknown intents cannot be bypassed by reseeding. Cold asset validation adds bandwidth without AI calls. Real notification/provider delivery, owner reading, scheduled invocations and local tests are separate evidence.
## Migration Plan
Complete specs/Gherkin before tasks, implement RED/GREEN and existing full local gate. Prepare exact candidate source/config/schema diff, verified Telegram owner identity and transfer procedure; then obtain any missing Git/production authority against that concrete candidate. Preserve existing Admin live business flags and deployed notification fix. Apply only additive0008 after exact-main CI and row-preservation checks; provision optional secrets privately and seed from original contiguous monitor evidence. Install fifteen-minute Admin schedule while preserving original search Cron. Qualify real delivery using one explicitly labelled monitor activation notification to the verified owner, real owner history, two naturally scheduled rounds, no search calls. Pause heartbeat only after all these pass, before original capacity expiry; otherwise leave it and report remaining evidence. Rollback disables only new monitor schedule/flag and retains all CMS intents; restore original heartbeat only within its original scope/expiry. Do not reset unknown intents, delete journals or renew capacity.
